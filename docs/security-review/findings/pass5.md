## Findings

### F-5-1: `burnSecret` and the `/burn` page send any fragment raw, so a share link given to them sends the seed to the server
Severity: Medium (it puts the seed on the server, which would be Critical, but only after a caller mistake or a user editing the path)
Location: `client/src/client.ts:87-89`, `client/src/client.ts:55-58`, `client/src/ui/burn.ts:14,28`, `client/src/ui/api.ts` (`burn`)
Violates: §12 Principle 1 ("no … seed ever reaches the server"), §2.11/§2.12
What: Share and burn fragments have the same shape on purpose (§2.11): version 0x01 followed by 32 bytes. Burning sends those 32 bytes as the raw `burn_token`. `burnSecret(link)` calls `parseFragment`, which keeps only what follows `#`, so `burnSecret("https://host/s#<seed>")` posts `{"burn_token": base64url(seed)}`. The seed then reaches the server, any TLS-terminating proxy, and anything that logs bodies. The website has the same problem when `/s#…` is edited to `/burn#…` and the user clicks the button. `report.ts:15-19` shows that path edits by users are expected.
Reproduction: `client/test/review_pass5.test.ts`, test "F-5: burnSecret given the SHARE link sends the raw seed to the server". The recorded request body's `burn_token` equals `toBase64Url(seed)`.
Fix: In `burnSecret`, when the input contains `://` or `/`, require the path to end in `/burn`. Make `revealSecret` require `/s` in the same way, and document that bare fragments are the caller's responsibility. The full fix is to make the two fragment kinds distinguishable: a distinct type byte for burn fragments, or a burn credential derived as `HKDF(burn_token, "shhnote/burn/v1")`. Both change the fragment format, so they need a spec revision and a version bump (§2.13).

### F-5-2: The client buffers the whole blob and copies it several times; decryption does not stream
Severity: Medium
Location: `client/src/ui/api.ts:110` (`await response.arrayBuffer()`), `client/src/crypto/chunks.ts:44-56` (`openAll` allocates the full plaintext), `client/src/crypto/container.ts:76` (`bytes.slice` per file), `client/src/ui/reveal.ts:155` (another copy in a `Blob`); create side `client/src/ui/create.ts:51`, `crypto/container.ts:43`, `crypto/padding.ts:47-48`, `crypto/chunks.ts:31`, `crypto/secret.ts:105`
Violates: D-4 and §2.7 ("decrypt while downloading, with memory bounded by the chunk size"), §12 Principle 9
What: On reveal, the client holds the ciphertext, the full padded plaintext, a copy of every file and a `Blob` copy at the same time, which is roughly 3–4× the blob size. On create it is roughly 5× (file buffer, `encodePayload` concat, `pad`'s inner concat plus the padded buffer, `sealAll` output, final `concat`). With `SHH_EXTERNAL_MAX_OBJECT` in the GiB range, a legitimate large file crashes the recipient's tab on phones and 32-bit devices. Because the client never compares the response length with `max_blob_bytes`, a hostile or misconfigured server can send an unbounded body.
Reproduction: Code reading of the lines above. Neither `decrypt` nor `openAll` accepts a stream, and `Api.reveal` reads the response with `arrayBuffer()` before decryption starts.
Fix: Add a streaming `openStream(ek, prefix, ReadableStream)` that reads in 65 552-byte units and holds back one unit to detect `last`. Write files incrementally, and refuse bodies longer than `blobLen` of the largest bucket the instance allows. Decrypt to a `Blob` assembled from parts, or to a stream download. The rest of the format is already built for this, so no spec change is needed.

### F-5-3: The client never uses the claim token, so the D-1 re-download path does not exist and library callers lose secrets
Severity: Medium (data loss for the recipient; nothing leaks)
Location: `client/src/ui/api.ts:110-111` (the claim header is read only after the body has fully arrived), `client/src/ui/reveal.ts:57` (`api.reveal(await lookup(seed))` never passes `claimToken`), `client/src/client.ts:62-83`
Violates: D-1 and §5.1 step 2 ("This is what makes a dropped download or a slow link cost nothing"), §2.10 step 4 ("retry locally")
What: (a) If the body fails mid-stream, `response.arrayBuffer()` throws a `TypeError` before `x-shh-claim-token` is read, so the token is lost. The page returns to "armed", and a second click reveals again without a token and gets the uniform 404, even though the claim window is open. (b) `revealSecret` decrypts inside the call and throws on a wrong passphrase without returning the blob or the claim token. A library caller cannot retry locally or re-download, so one typo destroys the secret. (c) `confirm: false` is documented as "keep a single-view secret downloadable until its claim window ends", but `RevealedSecret` does not include the token, so nobody can re-download or confirm.
Reproduction: `review_pass5.test.ts`, test "F-5: revealSecret never returns or reuses the claim token…". The result has no `claimToken`, a wrong passphrase rejects with `wrong_passphrase`, no recorded reveal body contains `claim_token`, and a body stream that errors after 100 bytes rejects with an error that is neither `ApiError` nor `ShhError`.
Fix: In `Api.reveal`, read the headers before the body and wrap body errors in an `ApiError(0, "network")` that carries the claim token. In `reveal.ts`, keep the claim token and retry `reveal(lookup, claimToken)` on a network failure while the window is open. In `client.ts`, return `claimToken` (or a `retry(passphrase)` handle) and stop throwing away the blob on `wrong_passphrase`. Update the `confirm` doc comment.

### F-5-4: Argon2 work memory (including the block that yields `pass_key`) stays unwiped in the cached WASM instance and in the core
Severity: Low (needs memory access; §10 calls scrubbing best effort)
Location: `Cargo.toml:14` (`argon2` with `features = ["alloc"]` only), `crates/shhnote-argon2-wasm/src/lib.rs:59-63`, `client/src/crypto/argon2.ts:43-64`, `client/src/ui/argon2-loader.ts` (the instance is cached for the life of the page), `crates/shhnote-core/src/kdf.rs:74-76`
Violates: §10 (best-effort scrubbing; the JS zeroes `pwd` and `out` but leaves the rest of the KDF state), Principle 12
What: `argon2` 0.6 allocates `m` KiB of blocks with `alloc_zeroed` and frees them with a plain `dealloc`, without wiping them, even when its `zeroize` feature is on (that feature only wipes H0 and the final block hash). With p = 1, `pass_key` is a hash of the last block, so the leftover memory gives `pass_key` directly, and H0 (the `zeroize` feature is off here) is enough to recompute it. In the browser, this memory lives in a WebAssembly memory that is cached and never shrinks, next to a seed that is never zeroed either (see F-5-5).
Reproduction: `review_pass5.test.ts`, test "F-5: Argon2 work memory is left unwiped inside the cached WASM instance". After one `hash` at m = 8 MiB, more than 7 MiB of the WASM memory (sampled every 64 bytes) is non-zero.
Fix: In the WASM crate, allocate the blocks yourself, call `hash_password_into_with_memory`, and wipe them before returning (`zeroize` is already a workspace dependency). Turn on `argon2/zeroize` in the workspace. Do the same in `kdf::argon2id` for parity.

### F-5-5: Memory scrubbing does less than the comments suggest, and the threat-model page lacks the caveat §10 says it has
Severity: Low
Location: `client/src/ui/reveal.ts:38-39` vs `:112` (`display` sets `blob = null` without wiping it, so the `pagehide` `blob?.fill(0)` never runs after a successful reveal); `seed` is never wiped (`reveal.ts:20`, `burn.ts:14`, `create.ts` `randomness.seed`); plaintext chunk copies are not wiped (`crypto/chunks.ts:18,23,52`, `own()` copies plus the decrypted chunk arrays); `crypto/padding.ts:48` (a `concat` copy of the payload that is never wiped); `crypto/container.ts:43` (the encoded payload is not wiped); `crypto/argon2.ts:45` (`pwd` copy in JS is not wiped); the passphrase input value is not cleared on reveal; `locales/en/main.ftl:315` (the threat-model "honest caveats" do not mention memory)
Violates: §10 ("best effort … and the threat model says so"); §2.4 wording ("the seed is the only key material that [exists as raw bytes in JS]") does not hold, since `pass_key` and `seed ‖ pass_key` exist briefly as `Uint8Array` (`secret.ts:67-70`), which the WASM boundary makes unavoidable
What: `padded.fill(0)` and the `pagehide` handler make the plaintext look wiped, but several plaintext copies and the seed stay on the heap until garbage collection. The "best effort" label is accurate. The threat-model page does not make the promise §10 says it makes, and §2.4 overstates the property.
Reproduction: Code reading of the lines above. After `display()` runs, `blob` is `null`, so `blob?.fill(0)` on `pagehide` does nothing.
Fix: Wipe `blob` in `display()` before dropping it, wipe `seed` on `pagehide`, wipe chunk buffers in `openAll`/`sealAll` and the intermediates in `encodePayload`/`pad`, and clear `passInput.value`. Add one line to the threat-model caveats ("your browser may keep decrypted data in memory until the tab is closed"). Revise §2.4 to say that the seed and, briefly, the Argon2 output are the only raw key material.

### F-5-6: TypeScript and Rust accept different manifests and treat an empty passphrase differently
Severity: Low
Location: `client/src/crypto/container.ts:26,52-66` vs `crates/shhnote-core/src/container.rs:359-372,437-438`; `client/src/crypto/secret.ts:87,131` and `client/src/ui/create.ts:57` vs `crates/shhnote-core/src/secret.rs:414-417,450`
Violates: §2.14 / Principle 11 (one protocol, proven by shared vectors); §2.5
What: The plaintext that reaches the parser is already authenticated, so only the sender controls these differences. They still let one blob decode differently in two conforming clients:
- A UTF-8 BOM before the manifest: TS accepts it (`TextDecoder` strips the BOM); Rust rejects it.
- Duplicate keys: TS keeps the last value, so `"text":"a","text":"b"` shows `b`; Rust rejects the manifest.
- `1.0` for `v` or `size`: TS accepts it; Rust rejects it.
- Lone-surrogate escapes: TS accepts them; Rust rejects them.
- A missing `text` key: Rust reads it as `null` and accepts; TS rejects.
- An empty passphrase: Rust's `encrypt(Some(""))` makes a passphrase blob that the TS client can never open, because `""` is falsy, so `decrypt` returns `passphrase_required` no matter what is entered.
Reproduction: The "PARITY:" and "RECORDS: an empty passphrase…" tests in `client/test/review_pass5.test.ts`, mirrored by `crates/shhnote-core/tests/review_pass5.rs` (`parity_*`). Both suites pass and show opposite decisions.
Fix: In TS, decode with `ignoreBOM: true` so the BOM is kept and `JSON.parse` rejects it, reject duplicate keys (a reviver or a scan of the raw keys), require `Number.isSafeInteger` together with the raw token having no `.`/`e`, and reject `\uD800`-style lone surrogates (`isWellFormed()`). In Rust, require `text` with `#[serde(deserialize_with)]` or a no-default wrapper. Choose one meaning for `""` (direct mode is the UI's choice) and apply it in `secret.rs`. Then add these cases to the vectors (see F-5-8).

### F-5-7: Hostile blobs can raise non-`ShhError` exceptions
Severity: Low
Location: `client/src/crypto/chunks.ts:47-48` (`out` is sized `body.length - count*16`, which is too small when the final fragment is shorter than a tag, so `out.set` throws `RangeError`), `client/src/crypto/container.ts:72` (`typeof meta.name` on a `null` entry throws `TypeError`), `client/src/ui/api.ts:110`
Violates: The `ShhError` contract in `crypto/error.ts:14` ("Every failure the crypto module can report"); Rust parity (Rust returns `Corrupt` for the same input)
What: A body of one full sealed chunk plus 1–15 bytes, which a hostile server or truncating proxy can send because the client does not check the length against the ladder, makes `decrypt` throw `RangeError: offset is out of bounds`. A manifest with `"files":[null]` throws `TypeError`. The website maps both to the "corrupt" message, so the visible effect is small. Third-party callers that branch on `e.code` get `undefined`.
Reproduction: `review_pass5.test.ts`, tests "F-5: a final fragment shorter than a tag escapes as a RangeError…" and "a null file entry surfaces as a TypeError…". Rust `short_final_fragment_is_corrupt_in_rust` returns `Corrupt`.
Fix: In `openAll`, reject when the final sealed chunk is shorter than `TAG_LEN + 1`, or simply require `(body.length - count*16)` to equal the sum of the chunk sizes, and throw `invalid_blob_length`. In `decodePayload`, check `typeof meta === "object" && meta !== null` first.

### F-5-8: The conformance vectors have no negative cases for most protocol paths
Severity: Low
Location: `vectors/generate.py:231-252`, `vectors/v1.json` (`reject[]`), `client/test/vectors.test.ts:175-205`
Violates: §2.14 (the vectors are "the tripwire"); README ("reject cases must fail for the stated reason")
What: All eight reject cases come from single-chunk vectors, and the clients skip `truncated` because the server would refuse its length. No vector covers chunks out of order, `last` on a middle chunk, a missing final chunk on a multi-chunk blob, a cut mid-chunk or a short final fragment, a header shorter than 95 bytes, `manifest_len` over 1 MiB or past the payload, file sizes that disagree with the remaining bytes (too large or too small), negative or fractional sizes, invalid UTF-8, a wrong manifest `v`, zero files with null text, `payload_len = 0`, `payload_len > bucket − 4` on a multi-chunk blob, or `t`/`p` below bounds and `p` above. None of the F-5-6 parity cases are covered either. Without them, the vectors cannot catch a lenient decoder (F-5-6 and F-5-7 slipped through for this reason).
Reproduction: `python3 -c "import json;print([r['name'] for r in json.load(open('vectors/v1.json'))['reject']])"` lists 8 cases. Every gap listed is now exercised in `client/test/review_pass5.test.ts` (sections "blob and chunk negatives", "container negatives") and `crates/shhnote-core/tests/review_pass5.rs`.
Fix: Add these as reject cases in `generate.py`. Container cases need a valid chunk layer around a malformed payload, which the generator already builds for `payload-len-too-large`. The vectors README forbids editing `v1.json` outside a protocol change. Adding rejects changes no protocol bytes, so either relax that rule for appended `reject[]` entries or ship them as `vectors/v1-reject.json`. That is a README decision, not a spec change.

### F-5-10: The download name is cleaned of `/` and `\` only
Severity: Low
Location: `client/src/ui/reveal.ts:158` (the shown name comes from `reveal.ts:148` via `textContent`, which is correct)
Violates: §2.5 ("sanitise before use as a download name")
What: Control characters (NUL, ESC), bidi overrides (U+202E turns `invoice‮fdp.exe` into the displayed name `invoiceexe.pdf`), look-alike slashes (U+2215), Windows reserved names (`CON`), leading dots and 10 000-character names all pass through. Browsers clean some of these themselves, inconsistently. The file card shows the spoofed name with no hint, which makes extension spoofing easy for a hostile sender.
Reproduction: `review_pass5.test.ts`, test "F-5: control, bidi-override and reserved characters pass through unchanged", which applies the exact expression from `reveal.ts:158`.
Fix: Normalise to NFC; replace C0/C1 controls, U+202A–202E, U+2066–2069, U+200E/F, `/ \ : * ? " < > |` and U+2215/U+29F8 with `_`; strip leading dots and trailing dots or spaces; cap the name at about 200 UTF-16 units while keeping the extension. Show the cleaned name on the card, or isolate the raw name with `<bdi>` / `dir="ltr"`.

## Suspicions

- **Sender-chosen MIME type on a same-origin `blob:` URL** (`reveal.ts:155`). `new Blob(bytes, { type: file.type })` with `type: "text/html"` or `image/svg+xml` gives an object URL in the shhnote origin. The `download` attribute protects a normal click, but "open link in new tab" or a drag to the tab bar navigates to it. Current Chromium and Firefox give `blob:` documents the creator's CSP (`script-src 'self'`, `form-action 'self'`), which should block scripts and cross-origin forms, but an HTML phishing page could still render under the site's origin. To confirm or clear: open such a link in Firefox ESR / Tor Browser and Chromium and check whether it renders and which CSP applies. Fix regardless: always create the Blob as `application/octet-stream` and keep `file.type` for display only.
- **Tor Browser "Safer" level disables WebAssembly** (I believe `javascript.options.wasm` is false there). Passphrase secrets would then fail with the generic "corrupt" message, which conflicts with Principle 9. Correctly, there is no fallback to anything weaker (see "Checked and clean"). To confirm: create and reveal a passphrase secret in Tor Browser at Safer. Fix: show a specific "this browser blocks WebAssembly" message.
- **WASM memory never shrinks.** A hostile blob within bounds (m = 256 MiB, t = 8) makes the tab keep about 260 MiB until it is closed, and one attempt can take more than 10 s on a phone. This is within §2.9, so it is accepted, but on 32-bit Android a grow failure is likely. `argon2` returns `OutOfMemory` (status 2 → `argon2_unavailable`) rather than trapping, which I checked in the crate source but not on a device.
- **`history.replaceState` runs only on successful reveal** (`reveal.ts:115`). On the "notfound" path (`reveal.ts:24,65`) and while waiting for a passphrase, the seed stays in the URL. For a TTL secret left at the passphrase prompt, the seed stays in the current history entry. The burn page scrubs on 404 as well. This is probably acceptable because the entry existed before the page ran, but it differs from burn.

## Checked and clean

- **Vectors:** both suites pass byte for byte. The TS and Rust vector tests replay the same `v1.json`.
- **Fragment** (TS `fragment.ts`/`bytes.ts`, Rust `fragment.rs`): exactly 44 base64url characters, at most one leading `#` removed. Rejected: the standard alphabet (`+`/`/`), `=` padding, leading, trailing or embedded whitespace, 43 or 45 characters, `##`, the empty string, and non-canonical trailing bits (canonical decoding on both sides). Version 0, 2 and 255 → `unsupported_version`. The version is checked once base64 decoding succeeds and before the seed is used anywhere.
- **`parseFragment`** takes the first `#`. A `#` cannot appear unescaped in a path or query, so a seed in the path or query is never picked up (`/s/<frag>` and `?k=<frag>` → `invalid_fragment`, and `#a#b` is rejected).
- **Key handling:** KEKs come from `deriveKey` and are non-extractable (`kdf.ts:56-58`). The content key is `generateKey(..., true, ["encrypt"])`, extractable only because `wrapKey` requires it. On reveal the content key comes from `unwrapKey(..., false, ["decrypt"])`. `exportKey` appears nowhere in `client/`. No key material reaches `console`, `localStorage`/`sessionStorage` (localStorage holds the theme only), IndexedDB, cookies or `innerHTML`. The share and burn links are put into the DOM on the create result, as designed. `console.error` calls log only error objects whose messages hold no key bytes.
- **Argon2 bounds:** checked in JS (`checkArgon2Bounds`, which also rejects NaN and non-integers) in `parseHeader` before any unwrap, again in `Argon2.hash` before the WASM call, and a third time inside WASM. The Rust core matches. The module is fetched same-origin at `/static/argon2.wasm?v=<hash>` and served as `application/wasm`, which `compileStreaming` requires. A failed load rejects, `loading` resets so the user can retry, and nothing falls back to anything weaker: `encrypt` refuses a passphrase without the module, `create.ts` fails the whole submit, and `reveal.ts` shows an error.
- **Mode detection:** the direct unwrap always runs first. Any blob that does not unwrap (wrong seed, tampered `wrapped_EK`, server-forged garbage) leads to the passphrase prompt. The passphrase is used only locally, each attempt is one user action (no loop), and the Argon2 cost of each attempt is bounded by §2.9. A blob cannot make a passphrase secret open without the passphrase (2⁻¹²⁸). No new information leaks, since the uniform server response already hides everything per secret.
- **Chunk layer:** order is enforced by the index in the nonce (reordered chunks, `last` on a middle chunk, a missing final chunk and a cut mid-chunk all → `corrupt`). Decryption is all-or-nothing (`openAll` buffers everything, see F-5-2), and `display()` runs only after the whole payload has decoded, so a failure at chunk i leaves nothing in the DOM.
- **Container:** `manifest_len` over 1 MiB and `manifest_len` past the payload are rejected; invalid UTF-8 is rejected (`fatal: true`); sizes that are too large, too small (trailing bytes), negative or fractional are rejected; zero files with null text → `empty_payload`; a wrong `v` is rejected; `payload_len > bucket − 4` → `corrupt` on single- and multi-chunk blobs. Empty and duplicate file names are accepted, since the spec does not forbid them; they are display data. `type` affects only the `Blob` MIME type (see the first suspicion).
- **API client:** every request goes to the caller-supplied base (trailing slashes trimmed) with `credentials: "omit"` and `cache: "no-store"`. Create sends `SHA-256(lookup)` and `SHA-256(burn_token)` (`secret.ts:113-114`, `api.ts:85-90`). Reveal, confirm and report send `lookup = HKDF(seed)` only, and the test checks that it is not the seed. Burn sends the raw burn token, as §2.12 prescribes for exercising a credential (but see F-5-1). Identifiers travel only in bodies.
- **CSP** (`web.rs:540`): `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; …`, with no `'unsafe-inline'` or `'unsafe-eval'`. The WASM is instantiated with `WebAssembly.compileStreaming`/`compile` plus `instantiate` with no imports. That needs exactly `'wasm-unsafe-eval'`, which Chromium (≥ 97), Firefox (≥ 102) and Tor Browser (ESR 115/128) support. No `eval`, `Function` or inline handlers in `client/src/`.
- **Padding and padmé:** TS and Rust agree on `padme`, `blobLen`, `chunkCount` and ladder selection, including above 2³¹ (BigInt). `unpad` behaves the same on both sides.
- **Header parsing** is identical: 95 bytes, the same offsets, bounds checked before anything else.
