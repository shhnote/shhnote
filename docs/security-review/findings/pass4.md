## Findings

### F-4-1: `GET /api/v1/config` leaks ~435 bytes of heap per request, unauthenticated and never rate-limited
Severity: High
Location: crates/shhnote-server/src/api.rs:168 (`Box::leak(Box::new((*state.settings.load()).clone()))`), route at api.rs:107
Violates: Principle 7 (operator cost hard-bounded); SPEC §4 (`GET /config` never limited, so nothing slows this)
What: The `/config` handler clones the whole `Settings` and leaks it with `Box::leak` so it can return `ConfigResponse<'static>`; the comment says "the settings live for the process", but a fresh copy is leaked on *every* request. Any client can grow the process's memory without limit just by fetching `/config`, which by spec is never rate-limited, until the process is OOM-killed.
Reproduction: `review_config_leak::spec_config_does_not_grow_memory`: "VmRSS before 19116 KiB, after 200000 GET /config 104236 KiB: +85120 KiB (435 bytes/request)". At a few thousand requests per second that is about 1 GiB every few minutes from one client.
Fix: Build the response from the `Arc<Settings>` snapshot. Either make `ConfigResponse` own its data (`Vec<u64>`, `Vec<i64>`, `Vec<Region>` cloned per request) or hold the `Arc` and serialize from a borrowed struct inside the handler (`let s = state.settings.load(); Json(ConfigResponse { ttl_presets: &s.ttl_presets, .. }).into_response()`, which serializes before `s` is dropped). No spec change.

### F-4-2: Security headers are missing from every API response, from the trailing-slash redirect, and from the API host in subdomain mode
Severity: Low
Location: crates/shhnote-server/src/web.rs:93-98 (the `security_headers` layer goes on the web router only); crates/shhnote-server/src/app.rs:21 (`web.nest("/api", api)` adds the API *after* that layer, so axum doesn't wrap it); app.rs:29 (subdomain: the API router never gets the layer); app.rs:32 (`redirect_trailing_slash` runs outside the layer)
Violates: SPEC §11 "Headers on every response: CSP …, HSTS (production), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, restrictive Permissions-Policy"
What: Every `/api/v1/*` response (reveal blobs, 404 uniform negatives, `/config`, `/health`, admin JSON, 405s, the API fallback) has no CSP, X-Frame-Options, nosniff, Referrer-Policy or Permissions-Policy. In production it also has no HSTS. The same holds for every response from `api.<host>` in subdomain mode and for the 308 trailing-slash redirect (`/en/` → `/en`). Blob responses served as `application/octet-stream` with no `nosniff` are the least comfortable case.
Reproduction: `review_headers::spec_every_response_has_the_security_headers` fails, listing 65 missing headers. Every `localhost/api/v1/*` row and `GET /en/` show `NO` for all five. `review_headers::spec_hsts_on_every_production_response` lists every `/api/v1/*` path and `/en/`. `records_headers_subdomain_production` shows the same for every `api.example.com` request. Pages, static assets, 404/405 pages and the locale redirect all have the headers.
Fix: Apply `security_headers` (the same `map_response_with_state`) as the outermost layer in `app::router`, after the nest and the host routing and outside `redirect_trailing_slash`. Then remove it from `web::router`. No spec change.

### F-4-3: Inline `style="…"` attributes on 7 templates, which the CSP blocks
Severity: Low
Location: crates/shhnote-server/templates/home.html:102; report.html:19; how_it_works.html:16,24,69,71; admin/keys.html:8; admin/dashboard.html:8; admin/reports.html:8; admin/settings.html:8,27,53
Violates: SPEC §10 "no inline scripts or styles anywhere", §11; web-page skill "No inline `<script>`, `<style>`, `style=` …: the Content Security Policy blocks them"
What: These templates use `style=` attributes. `style-src 'self'` without `'unsafe-hashes'` or `'unsafe-inline'` blocks them, so the intended spacing and alignment never apply and every load logs CSP violations. No inline `<script>` (apart from the JSON i18n block), `<style>` or `on…=` was found on any page, including the Markdown pages and the error pages.
Reproduction: `review_headers::spec_no_inline_styles_or_scripts_on_any_page` fails with the list above (`/en`, `/de`, `/en/report`, `/en/how-it-works`, all four admin pages).
Fix: Move each one into a utility class in `static/app.css` (e.g. `.mt-2`, `.gap-3`, `.text-center`). No spec change.

### F-4-4: Bootstrap sessions are only suspended, not ended, when an admin key is created, and they are not bound to the token
Severity: Low
Location: crates/shhnote-server/src/admin.rs:145-157 (`authenticate` → `bootstrap_allowed` only checks "token configured and zero admin keys right now"); admin.rs:244-249 (the session names `hash` of the token but `authenticate` never compares it with the current `admin_token_hash`)
Violates: SPEC §8 "bootstrap sessions end the moment an admin key is created"; D-9 ("the token is retired")
What: A bootstrap cookie issued before the first admin key existed is refused while admin keys exist. Once they are gone again (`shhnote reset-admin`, or an admin deleting the last admin key), the old cookie is accepted again for the rest of its 12 h. The cookie also stays valid after the operator changes `SHH_ADMIN_TOKEN`, because only the bootstrap flag is checked, not which token the session was made for. In practice this needs a captured cookie younger than 12 h plus a reset, or a token rotation.
Reproduction: `review_admin::spec_bootstrap_session_does_not_come_back`: the old cookie gets 303 while an admin key exists and 200 after `store.delete_admin_keys()`. `review_admin::records_bootstrap_cookie_outlives_token_rotation`: a cookie from token A gets 200 on a server configured with token B (same DB and `SHH_SECRET_KEY`).
Fix: In `authenticate`, for bootstrap sessions also require `session.key_hash == admin_token_hash` (constant-time). To make "ended" permanent without server state, refuse bootstrap sessions whose issue time (`expires - SESSION_SECS`) predates the latest admin-key deletion. That needs a stored timestamp, so the simpler option is a spec note that `reset-admin` revives bootstrap cookies younger than 12 h and that operators should also rotate `SHH_SECRET_KEY`. Choosing between the two needs a small spec decision.

### F-4-5: Logout does not check the CSRF token, and logging out doesn't revoke the session
Severity: Low
Location: crates/shhnote-server/src/admin.rs:262-268 (`logout` takes no session or form); templates/partials/admin_nav.html:7-10 (the form sends `csrf`, which is ignored)
Violates: SPEC §8 "Forms carry a CSRF token derived from the session; a request without it gets 403"; web-page skill "Every form that changes data must be protected against CSRF"
What: `POST /{locale}/admin/logout` succeeds with no cookie and no token. Today SameSite=Strict is the only thing stopping a cross-site forced logout. Logout only clears the cookie in the browser, so a copy of the cookie stays valid until its 12 h expiry. The spec's stateless design accepts that last part, but neither the spec nor the UI says so.
Reproduction: `review_admin::spec_logout_requires_csrf`: logout without csrf gets 303 (expected 403). `review_admin::records_cookie_survives_logout`: the old cookie gets 200 on `/en/admin` after logout.
Fix: Authenticate and `check_csrf` in `logout` like the other POST handlers. To revoke on logout without server state, put a per-key "sessions valid after" timestamp in `api_keys`. Revocation on logout needs a spec decision; the CSRF check does not.

### F-4-6: Admin pages, including the one that shows a newly minted API key, are cacheable, and the admin API's 401 has no `no-store`
Severity: Medium
Location: crates/shhnote-server/src/admin.rs:596-616 (`render_keys` → `render`, no Cache-Control), admin.rs:637 (the new key is rendered into the POST response); every admin handler; crates/shhnote-server/src/admin_api.rs:69-85 (`no-store` is added only on the success path)
Violates: web-page skill "Pages showing secret content also send `Cache-Control: no-store`"; SPEC §8 "responses are `no-store`" (admin API); §2.12 intent (an API key is a credential)
What: The keys page shows a new admin or user key "exactly once", but the response has no `Cache-Control`, so browsers may keep it in the HTTP disk cache or the back-forward cache. Anyone who later reads that browser profile, or presses Back on a shared machine, can recover a full admin credential. The other admin pages (stats, reports ledger, settings, key list) also carry no `no-store`, and neither do the admin API's 401/429 replies.
Reproduction: `review_admin::spec_admin_pages_are_no_store` fails: "POST /en/admin/keys (new key shown) cache-control: None", plus `/en/admin`, `/en/admin/settings`, `/en/admin/reports`, `/en/admin/keys`, `/en/admin/login` and `GET /api/v1/admin/stats (401)`.
Fix: Add `Cache-Control: no-store` to every response under `/{locale}/admin` (a layer on `admin::routes()`) and to every `require_admin` response, error or not. No spec change.

### F-4-7: Settings validation accepts values that break the instance or the spec's invariants, some of which cause panics
Severity: Medium
Location: crates/shhnote-core/src/settings.rs:117-208 (`with_overrides`: type parsing only, no ranges); crates/shhnote-store/src/secrets.rs:112 (`now + window_secs`); crates/shhnote-server/src/ratelimit.rs:120 (`per_hour * user_multiplier`); crates/shhnote-server/src/api.rs:341 (`2 * text_max_bytes + 1024`); crates/shhnote-server/src/admin_api.rs:223-261 and admin.rs:458-510 (both rely on `with_overrides`)
Violates: D-6 ("with a 64 KiB minimum padded size"), D-7 (14-day max, silently clamped rather than rejected), SPEC §8 ("validated as a whole"), Principle 12 (relaxing a default must be an explicit step, not a typo)
What: PATCH `/api/v1/admin/settings` and the settings form accept all of these with 200: `padding_min` 0 or 1; a buckets ladder `0,1,5`; `claim_window_secs` −1, 0 or i64::MAX; `min_ttl_secs` −100; `ttl_presets` of 30 days or −5; `text_max_bytes` 0 or u64::MAX; `rate_user_multiplier` u32::MAX or 0 (0 means *unlimited* for user keys, because a product of 0 disables the bucket); `salt_rotation_secs` −1; `daily_retention_days` i64::MAX; `max_ttl_secs` 30 days (stored silently as 14 days). Consequences seen in tests: with `padding_min=0` a blob with a 1-byte bucket (112 bytes) is accepted, so the server and any dump learn small-secret sizes. With `claim_window_secs=i64::MAX` every single-view reveal panics with "attempt to add with overflow" (debug; in release it wraps to a past expiry and the claim lapses at once). With `rate_user_multiplier=u32::MAX` every user-key request panics with "attempt to multiply with overflow". Validation is whole-settings in the sense that one bad field rejects the save, but range and cross-field checks only exist for the TTL triple and retention.
Reproduction: `review_admin::spec_settings_patch_rejects_values_that_break_the_instance` (lists every accepted value), `records_padding_min_zero_accepts_tiny_blobs` (create with bucket=1 → 201), `records_huge_claim_window_panics_reveal`, `records_huge_user_multiplier_panics_keyed_requests` (both `JoinError::is_panic()`).
Fix: Add bounds in `with_overrides`, so the panel, the API and database loading all reject them: `padding_min ≥ 65536` (or spell out in the spec whether D-6's minimum is a floor or a default); ladder entries strictly increasing, ≥ `padding_min` and ≤ `SHH_EXTERNAL_MAX_OBJECT`; `60 ≤ claim_window_secs ≤ 86400`; `min_ttl_secs ≥ 60`; presets within `[min_ttl, max_ttl]`; `max_ttl_secs > 14 d` rejected rather than clamped; `1 ≤ text_max_bytes ≤ 1 MiB` (the manifest limit); `rate_user_multiplier ≥ 1` with saturating multiplication; `salt_rotation_secs ≥ 60`; retention capped. Use `saturating_add`/`checked_mul` at the three arithmetic sites as well. D-6 wording needs a spec clarification.

### F-4-8: The admin API looks up the credential before checking the login bucket, so a rate-limited client can keep guessing
Severity: Low
Location: crates/shhnote-server/src/admin_api.rs:37-85 (`find_api_key` / bootstrap compare first, `limiter.check(Endpoint::Login, …)` only on failure)
Violates: SPEC §8 "Failed authentications share the login rate limit" (the limit is meant to slow guessing)
What: Once a client has used up its login bucket, wrong guesses get 429 but a correct guess still gets 200. The limit only changes the error code and never stops a search. The web login checks the bucket first (`admin.rs:221`) and does block. With 256-bit keys and a bootstrap token of at least 32 characters (enforced in `config.rs:554`) brute force isn't practical, so this is hardening.
Reproduction: `review_admin::spec_admin_api_limit_blocks_guessing`: after 25 wrong guesses, "correct credential while limited -> 200 OK". `records_login_failures_look_alike_and_are_limited` confirms the web login returns 429 even for the right credential once limited.
Fix: Peek at the bucket before the lookup, without spending a token, and answer 429 when it is empty. Spend a token only on failure, so a legitimate admin isn't charged for successes. No spec change.

### F-4-9: Hex parsing of key ids panics on non-ASCII input (admin API and panel)
Severity: Low
Location: crates/shhnote-server/src/admin_api.rs:368-376 and crates/shhnote-server/src/admin.rs:717-725 (`&text[i..i + 2]` slices bytes of a `&str`)
Violates: CLAUDE.md (`log_error!` for diagnostics, never panics in handlers); High-class pattern "remotely triggerable crash", but only an authenticated admin can reach it
What: `unhex` checks the byte length, then slices at byte offsets. An id like `"0é" + 61 × "0"` (64 bytes) slices through the middle of `é` and panics. The request task dies (no response; hyper drops the connection) and a Rust panic message goes to stderr, bypassing `SHH_LOG_LEVEL`. `from_str_radix` also accepts a leading `+`, so ids are parsed loosely.
Reproduction: `review_admin::spec_admin_key_delete_does_not_panic_on_non_ascii`: "handler panicked: JoinError::Panic(… 'end byte index 2 is not a char boundary; it is inside 'é' …')". The same input to the panel's `key_hash` field hits the same code after authentication and CSRF.
Fix: Reject non-ASCII-hex input before slicing (`text.bytes().all(|b| b.is_ascii_hexdigit())`) or decode byte pairs with `u8::from_str_radix(std::str::from_utf8(&bytes[i..i+2])?, 16)`. Require exactly 64 characters in the panel too. No spec change.

### F-4-10: Region URLs and `source_url` are rendered into `href` with no scheme check
Severity: Low
Location: crates/shhnote-core/src/settings.rs:135-137, 174-176 (no URL validation); crates/shhnote-server/templates/home.html:92 (`href="{{ r.url }}"`); base.html:58 and how_it_works.html:144 (`href="{{ ctx.repo_url() }}"`); contact.html:15,19 (`mailto:{{ … }}`)
Violates: Principle 12 (secure by default); SPEC §9 (regions are sibling-instance URLs, i.e. `https://` origins)
What: An admin, or anyone holding an admin key, can set a region URL or the source link to `javascript:…` or `data:text/html,…`, and it is rendered as a clickable link on the public create page and in the footer of every page. Askama escapes the markup correctly (`<script>` in the site name, `<b>` in a region name and `"><img …>` in the contact email all came out escaped), but escaping doesn't touch the scheme. The CSP (no `'unsafe-inline'`) blocks `javascript:` execution and browsers block top-level `data:` navigation, so today the effect is a dead or phishing link rather than XSS.
Reproduction: `review_admin::records_settings_rendered_into_pages`: `home contains href="javascript:alert(1)": true`, `href="data:text/html: true`, `href="javascript:alert(document.domain)": true`, with all markup escaped.
Fix: In `with_overrides`, accept only `https://` (and `http://` when `SHH_ENV=local`) with a host and no userinfo for `regions[].url` and `source_url`. Check that `contact_email` and `security_email` contain no `?`, `#`, `/` or whitespace. No spec change.

### F-4-11: JSON body rejections on secret endpoints and the admin API bypass the shared error type
Severity: Low
Location: crates/shhnote-server/src/api.rs:354, 440, 458, 481 (`Json<…>` extractors on reveal/confirm/burn/report); admin_api.rs:225, 323, 353
Violates: api-endpoint skill (one error type, "always returns the same JSON shape"; "Uniform negatives … malformed input"); SPEC §4 (every negative outcome on a credential endpoint is the same 404)
What: A body that isn't JSON, lacks a field, or has the wrong `Content-Type` makes axum's default rejection answer `400`/`415`/`422` with a `text/plain` body before the handler runs, instead of the uniform 404 JSON. The difference depends only on the request's shape, never on any secret's state, so nothing per-secret leaks. It is still a second negative format on endpoints the spec says have exactly one. (Pass 1 owns uniformity; recorded here because the header walk surfaced it.)
Reproduction: in `review_headers::records_headers_path_routing`, `POST /api/v1/secrets/reveal` with body `not json` gets `400 text/plain`, while `{"lookup":"x"}` gets `404 application/json`.
Fix: Use a custom extractor (or `WithRejection`) that maps any JSON rejection on credential endpoints to `uniform_negative()` after running the random-bytes path, and to the shared `ApiError` shape on the admin API. No spec change.

### F-4-12: Key creation and settings save render the POST response directly (no POST/redirect/GET)
Severity: Low
Location: crates/shhnote-server/src/admin.rs:500-509 (settings save), 636-639 (key create)
Violates: web-page skill "Forms that change data use POST and redirect after success (POST/redirect/GET), so refreshing doesn't resubmit"
What: Reloading after creating a key resubmits the form, which still carries a valid CSRF token, and mints another key with the same name and scope. Showing the key once needs the POST response, which is a reasonable exception, but the resubmit should then be harmless.
Reproduction: `review_admin::records_key_create_resubmit_mints_again`: two identical POSTs (same cookie, same CSRF token) both get 200 and leave 2 keys in `api_keys`.
Fix: Settings: redirect to `/admin/settings?saved=1`. Keys: either accept the exception and add a one-time nonce to the form (stored in the cookie MAC input) so a resubmit is refused, or document the exception in the skill.

## Suspicions

- **`event.isTrusted` on `submit` does not prove a user gesture.** In `client/src/ui/reveal.ts:48-50` (also `burn.ts:21-23`, `report.ts:63-65`), the guard checks `isTrusted` on the form's `submit` event. Per the DOM and HTML specs, a submit event that the user agent fires as part of form submission is trusted even when a script started it: `form.requestSubmit()`, or `button.click()` (where only the synthetic *click* is untrusted). So any script running in the page, such as an extension content script or a scanner that drives the DOM from JS rather than through CDP input events, can consume a single-view secret. SPEC §5 says "responds only to a trusted user gesture". No browser was available here to confirm. To confirm: load `/en/s#<valid fragment>` in Chromium and Firefox, run `document.querySelector('[data-reveal-form]').requestSubmit()` in the console, and see whether a `POST /secrets/reveal` goes out. If it does, put the guard on the button's `click` (with `event.isTrusted && event.detail > 0`, or a separate `keydown` handler for Enter/Space) and/or require `navigator.userActivation?.isActive` where available. Tor Browser (Firefox ESR) support for `userActivation` would need checking.
- **The login bucket is shared behind an unconfigured proxy.** If the instance sits behind a reverse proxy that isn't in `SHH_TRUSTED_PROXIES`, every visitor shares the proxy's IP, so anyone can use up `rate_login_per_hour` (20) and lock the admin out of the web login for an hour (the web login refuses even the right credential when limited). This is a deployment issue that pass 1/6 may cover; a `docs/deploy` note would close it.
- **The reveal `notfound` state leaves the fragment in the URL** (`reveal.ts:24, 65` don't call `history.replaceState`). SPEC §10 only requires scrubbing after reveal and burn. A dead link's seed staying in history is harmless, but it is inconsistent with the burn page, which scrubs on 404.

## Checked and clean

- Session cookie: `shh_admin=<b64(flag‖key_hash‖expires‖nonce)>.<b64(HMAC-SHA256(SHH_SECRET_KEY, payload))>`. Set-Cookie seen: `Path=/; HttpOnly; SameSite=Strict; Max-Age=43200` (`Secure` added when `SHH_ENV=production`, `admin.rs:121-131`). The MAC is checked in constant time before any field is used. Tampered expiry, a flipped bootstrap flag, junk and empty values, and a cookie signed under a different `SHH_SECRET_KEY` are all refused (`clean_tampered_expiry_and_garbage_cookies_are_rejected`). Rotating `SHH_SECRET_KEY` ends every session and invalidates every CSRF token. Expiry is enforced server-side (`expires <= now()`).
- Every admin page request re-checks the key: `find_api_key(session.key_hash)` with `Scope::Admin`. Deleting the key ends its sessions, and a user-scope key cannot log in (existing `admin_login_bootstrap_then_keys`, plus `records_login_failures_look_alike_and_are_limited`).
- CSRF token = `HMAC(SHH_SECRET_KEY, "csrf" ‖ session nonce)`, domain-separated from the session MAC (different input length and prefix) and different for each login. It is checked in constant time on settings save, key create and key delete. A missing, wrong or other-session token gets 403 (`clean_csrf_checked_on_settings_and_keys`). Logout is the exception (F-4-5).
- The admin JSON API accepts only `Authorization: Bearer`. Admin cookies are refused there (401), so it has no CSRF surface. A user key on an admin route gets 401. An admin key on a user route is treated as anonymous. The bootstrap token stops working on the API as soon as an admin key exists (`records_bearer_parsing_and_scopes`). Bearer parsing: the `Bearer` scheme is case-sensitive (`bearer x` gets 401, which differs from RFC 7235 but fails closed). Extra spaces and trailing whitespace are trimmed. An empty token, a missing scheme and `Basic` all get 401.
- Login: an unknown credential and a valid user key give byte-identical 401 pages, so a failed login doesn't reveal whether a key exists. Keys are looked up by `SHA-256(credential)` in an index, and the bootstrap token is compared to its hash in constant time. The web login checks the bucket before the credential. `reset-admin` → `delete_admin_keys` brings the bootstrap token back (existing test).
- Settings validation is whole-settings: a single bad field rejects the whole PATCH or form with 422 (`invalid_settings`) and changes nothing. The range checks are what's missing (F-4-7).
- Askama auto-escaping is in effect for every `{{ }}` in `.html` templates. The only `|safe` uses are `doc.html:10` (first-party Markdown compiled into the binary) and `base.html:19` (`ui_json`, Fluent strings JSON-encoded with `<` escaped to `<`, inside `<script type="application/json">`). A site name with `<script>`, region names with markup and a contact email with `">` all render escaped on public and admin pages.
- Markdown: pulldown-cmark with tables and smart punctuation. Raw HTML passes through and link schemes aren't filtered, but the only input is `content/{en,de}/*.md` built into the binary. The `{{site_url}}`/`{{api_url}}` substitutions come from deployment config, not settings. The `<…>` placeholders in docs.md sit inside code blocks and are escaped. The rendered doc pages have no inline script or style.
- The CSP matches SPEC §10: `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; font-src 'self'; img-src 'self' data: blob:; connect-src 'self' [api origin]; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`. It is present on every page, static asset, 404, 405 and locale redirect. HSTS (`max-age=63072000; includeSubDomains`) is on all web responses in production. The gaps are listed in F-4-2.
- Static assets: fixed routes only. `/static/../Cargo.toml`, `%2e%2e`, `/static//etc/passwd` and `/static/app.js/..` all get 404, and the fallback refuses everything under `/static/`. `?v=` is ignored (any value serves the current asset, which is harmless). `argon2.wasm` is served as `application/wasm` (streaming compile works). Assets get `public, max-age=31536000, immutable`. `/s`, `/burn` and blob responses get `no-store`, and the two never overlap.
- Locale handling: path locales are exactly the offered ones (`/fr/...` falls through to the redirect, so `/en/fr/...` gives 404). Hostile `Accept-Language` values (60 KB of tags, `q=NaN`, `q=inf`, duplicates, `;;;,,,;q=,`) all give 307 to `/en/s` or `/de/s`. The locale redirect builds `/{locale}{path}[?query]` and always starts with `/xx/`; `//evil.com`, `/\evil.com`, `/%2F%2Fevil.com` and `?next=//evil.com` all stay on-site. The trailing-slash redirect collapses leading `/` and `\`. Location never carries a fragment, so the browser keeps the original one. `Vary: Accept-Language` is set. Language links with `data-keep-hash` copy the fragment on click, same-origin only.
- Interstitial (`secret.html`, `reveal.ts`): on load the script only decodes `location.hash` locally and shows the form. `lookup()` and `api.reveal()` run only inside the `submit` handler after `isTrusted` (but see Suspicions). Nothing reads `document.referrer`, no fetch happens on load, and argon2.wasm is fetched only when a passphrase is needed. The fragment is scrubbed with `replaceState` after display. `fetch` uses `credentials: "omit"` and `cache: "no-store"`. No expiry or lifetime information appears before reveal.
