## Findings

### F-6-1: The Docker quick start leaves `.env` world-readable
Severity: Low
Location: README.md:22-23 (`curl … -o .env`, `docker run --rm ghcr.io/shhnote/shhnote init >> .env`); docs/deploy/docker.md:13-21; deploy/docker/.env.example:21-25; crates/shhnote-server/src/init.rs:82-131 (`write_atomically` keeps an existing file's mode by design)
Violates: Principle 12 (secure by default); SPEC §7.1 (`SHH_SECRET_KEY`, `SHH_ADMIN_TOKEN`, `SHH_PG_PASSWORD`, `SHH_S3_SECRET_ACCESS_KEY` are credentials); CLAUDE.md ("`.env` … holds credentials")
What: The quick start creates `.env` with `curl -o` under the user's umask (0644 on a stock host) and appends the two secrets with a shell redirect, so the file that holds the session-signing key, the bootstrap admin token and, with the Postgres or S3 profile, the database password and object-store keys is readable by every local account. Neither README.md, docs/deploy/docker.md nor the header of deploy/docker/.env.example sets a mode, while the systemd guide does (`chmod 0640`). `shhnote init --env` deliberately keeps an existing file's permissions (SPEC §8), so it cannot repair this either; only a newly created file is 0600.
Reproduction: in an empty directory with `umask 022`: `printf 'SHH_DB=sqlite\n' > .env; docker run --rm <image> init >> .env; ls -l .env` → `-rw-r--r--` with both secrets inside (run here against the freshly built image). `review_r2_pass6_init_env_modes` pins that `init --env` keeps a 0644 file at 0644 and creates a new file at 0600.
Fix: in README.md, docs/deploy/docker.md and the `.env.example` header, fetch the file under `umask 077` or add `chmod 600 .env` right after the `init` line (and `chmod 600` in the "with your own reverse proxy" and Postgres sections, since the same file gains `SHH_PG_PASSWORD`). Optionally let `init` (both forms) print a one-line reminder about the mode to stderr. No spec change.

### F-6-2: A single tag push by any write-access account publishes npm, the image and the release, with no environment protection
Severity: Low
Location: .github/workflows/release.yml:3-5 (trigger `push: tags: ["v*"]`), :110-144 (`publish`: `id-token: write`, `npm publish … --provenance`), :81-108 (`release`: `contents: write`), :203-241 (`manifest`: `packages: write`, tags `latest`)
Violates: Principle 11 (auditable supply chain), Principle 12
What: Trusted publishing moves the npm trust anchor from a token to "this repository's `release.yml`". Whoever can push a `v*` tag (every collaborator with write access, or anyone holding such a collaborator's PAT or SSH key) can therefore publish a new `@shhnote/client` version, push a `latest` image and create a GitHub release whose provenance attestations will vouch for the content, since the `version` and `ci` gates only check that the tag matches the files and that the tests pass on whatever commit was tagged. None of the three publishing jobs runs in a GitHub `environment`, so there is no required-reviewer step and no way to restrict the OIDC token to a protected context; whether a tag ruleset limits who may create `v*` tags is a repository setting that is not visible in the tree. Pre-release tags skip npm (the dash check) but still publish the image and release.
Reproduction: read the workflow; `grep -n "environment:" .github/workflows/release.yml` returns nothing.
Fix: give `publish`, `release` and `manifest` an `environment: release` with required reviewers (and a deployment-branch/tag rule for `v*`), register that environment name in the npm trusted-publisher configuration so the OIDC token is only honoured from it, and add a repository ruleset that restricts creation of `v*` tags to maintainers. All GitHub/npm-side; no spec change.

### F-6-3: Advisory checks only run on pushes; nothing bumps pinned actions, images or lockfiles
Severity: Low
Location: .github/workflows/ci.yml:3-8 (`on: push, pull_request, workflow_call`, no `schedule`), :87-104 (`audit` job); Dockerfile:10 (`rust:1.99-alpine@sha256:7e9e2d…`); absence of `.github/dependabot.yml` or a Renovate config
Violates: Principle 11
What: The `audit` job (cargo deny, npm audit) runs when something is pushed. A RustSec or npm advisory published while `main` is idle is not surfaced until the next push or tag (the release still calls CI, so a release is gated, but an advisory against the version already deployed goes unnoticed). Every supply-chain pin that round 1 introduced (action SHAs, image digests, `Cargo.lock`, `package-lock.json`) now moves only by hand; the `rust:1.99-alpine` digest is already one rebuild behind its tag (same Rust 1.99.1, newer base image). Pins without a bump mechanism quietly become stale pins.
Reproduction: `grep -n schedule .github/workflows/*.yml` → nothing; `ls .github` → `workflows` only; `docker buildx imagetools inspect rust:1.99-alpine --format '{{.Manifest.Digest}}'` → `sha256:27cd9b…` vs the pinned `sha256:7e9e2d…`.
Fix: add a `schedule:` (weekly) trigger that runs the `audit` job alone; add `.github/dependabot.yml` covering `github-actions`, `docker` (root `Dockerfile`, `deploy/docker/docker-compose.yml`, the CI service image), `cargo` and `npm` (`/client`), grouped and with a weekly cadence so the SHA/digest comments stay honest. No spec change.

### F-6-4: The bare-metal Caddyfile has no `admin.` block while the docs say to add one
Severity: Low
Location: deploy/caddy/Caddyfile:1-10 (only the site and the commented `api.` block); deploy/docker/Caddyfile:14-19 (the `admin.` block with the `remote_ip` allow-list); docs/deploy/reverse-proxies.md:7 ("the same goes for `admin.<domain>` with `SHH_ADMIN_ROUTING=subdomain`, which is also where to put an IP allow-list"); docs/deploy/bare-metal.md:56-66
Violates: SPEC §8 / D-25 ("a subdomain is easy to firewall"); Principle 12 (docs must match the shipped examples)
What: `SHH_ADMIN_ROUTING=subdomain` was added in revision 2 with the stated purpose of letting operators firewall the panel. The Docker Caddyfile shows the pattern (a site block for `admin.{$DOMAIN}` with `@outside not remote_ip … respond 404`); the bare-metal Caddyfile, which the bare-metal guide tells operators to copy, carries only the `api.` example. A bare-metal operator who switches the panel to a subdomain gets no site block (Caddy answers an empty 200 for an unknown host, so the panel is simply unreachable until they write one) and no hint of the allow-list that is the point of the mode.
Reproduction: `diff deploy/caddy/Caddyfile deploy/docker/Caddyfile`.
Fix: mirror the commented `admin.secrets.example.com` block (with the `remote_ip` example) into deploy/caddy/Caddyfile and reference it from bare-metal.md step 4. Documentation only.
