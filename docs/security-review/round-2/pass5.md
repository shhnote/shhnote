## Findings

### F-5-1: The reference reveal page caps the decoder at the instance maximum, not the response length, so a 64 KiB hostile blob makes the recipient reserve up to `max_blob_bytes`
Severity: Low
Location: `client/src/ui/reveal.ts:130-131,154` (`maxBlobBytes = pageMaxBlobBytes ?? config.max_blob_bytes`, then `decryptBody(ek, header, rest, maxBlobBytes)`; `revealed.contentLength` is never read), `client/src/crypto/stream.ts:110,142` (the length prefix is checked against `maxPayload`, then every file buffer is allocated at its manifest size before any file byte has arrived)
Violates: D-4 / SPEC §2.7 ("memory bounded by the chunk size"), §10 ("refuses a body longer than … both as announced and as received"), `docs/frontend-conformance.md` item 6 ("bounded client memory whatever the server sends")
What: `revealSecret` bounds the decoder with `Math.min(maxBlobBytes, contentLength)` (`client.ts:125`), so a length prefix larger than the blob is refused before anything is allocated. `wireReveal` passes the instance maximum instead. A sender who uploads a one-bucket blob whose `payload_len` and manifest claim a file of `max_blob_bytes − 95` bytes makes every recipient's browser allocate that much (`new Uint8Array(f.size)` for each file) before the stream ends and the decoder reports the truncation. The server has always sent `Content-Length` (set from the bucket, §6.1), so the information is there and the library path already uses it. The amplification is 64 KiB uploaded → up to the instance's external cap (4 GiB at most) reserved per recipient; on most browsers a multi-GiB allocation fails with a `RangeError`, which the page shows as "corrupt", so the practical effect is a crafted secret that cannot be opened and, on a single-view secret, is consumed. The passphrase path is not affected: it passes the collected length (`bytes.length + HEADER_LEN`, `reveal.ts:189`).
Reproduction: `client/test/review_r2_pass5.test.ts`, "F-5-1: decryptBody capped at the instance maximum, as wireReveal passes it, reserves the claimed file size before the truncation is seen": a 65 647-byte blob claiming a 48 MiB file makes `decryptBody(…, DEFAULT_MAX_BLOB_BYTES)` grow `process.memoryUsage().arrayBuffers` by ≥ 48 MiB before rejecting with `corrupt`; the same blob with the cap set to the blob length rejects without the allocation.
Fix: in `reveal()`, pass `Math.min(maxBlobBytes, revealed.contentLength ?? maxBlobBytes)` to `decryptBody`, as `revealSecret` does. Independently, `PayloadDecoder` could cap the total of the manifest's sizes at `maxPayload − 4 − manifestLen` before allocating (it already computes `remaining`), and allocate file buffers lazily as bytes arrive. No spec change.

### F-5-2: Nothing from `/config` or the response headers is validated, so a non-numeric `max_blob_bytes` or `Content-Length` disables the body cap, and a numeric one is not clamped to the 4 GiB ceiling
Severity: Low
Location: `client/src/lib/api.ts:119-120` (`response.json() as InstanceConfig`, no checks), `client/src/lib/api.ts:146-150` (`Number(length)` → `NaN` passes `contentLength > maxBytes` and poisons `Math.min`), `client/src/lib/api.ts:98` (`seen > NaN` is false), `client/src/client.ts:118,125` (`opts.maxBlobBytes ?? config.max_blob_bytes`, no `Math.min(…, DEFAULT_MAX_BLOB_BYTES)`), `client/src/ui/reveal.ts:130`, `client/src/crypto/stream.ts:110`
Violates: SPEC §10 (the body cap is "the instance's `max_blob_bytes` … or a smaller cap"), §7.1 (`SHH_EXTERNAL_MAX_OBJECT` is "at most 4 GiB", which is what `DEFAULT_MAX_BLOB_BYTES` encodes as the ceiling per `api.ts:6-8`), conformance item 6
What: `getConfig` returns whatever JSON the instance sends. `max_blob_bytes: "unlimited"` (or any non-number) turns every comparison in `Api.reveal`, `cappedBody` and `PayloadDecoder` into a comparison with `NaN`, all false, so the body streams without any limit; a value above 4 GiB is used as given. A malformed `Content-Length` has the same effect on the as-received cap (`Number("abc")`). Browsers refuse responses with an unparsable `Content-Length`, so that half needs a custom `Fetch`; the `/config` half needs only an instance that is hostile or misconfigured, and the instance is exactly the party the cap is meant to bound. `fragment_version`, `padding`, `ttl_presets` and the rest are likewise unchecked: a wrong type there fails closed (`includes` on a string version → `unsupported_protocol`; `ladder.find` on a non-array throws inside the create path and surfaces as "failed"), so only `max_blob_bytes` fails open.
Reproduction: `review_r2_pass5.test.ts`, "F-5-2: a non-numeric max_blob_bytes from /config switches the body cap off instead of failing closed" (an instance answering `max_blob_bytes: 100` makes `revealSecret` throw `too_large`; the same body with `max_blob_bytes: "unlimited"` decrypts; with `2 ** 50` the value is used unclamped) and "F-5-2: a malformed Content-Length disables the as-received cap in Api.reveal" (a 10-byte cap lets 1000 bytes through).
Fix: validate `InstanceConfig` in `getConfig` (every numeric field `Number.isSafeInteger` and in range, `padding` of the right shape, `fragment_version` an integer) and throw `ApiError(0, "invalid_config")` otherwise; compute the cap as `Math.min(configured, DEFAULT_MAX_BLOB_BYTES)`; treat a `Content-Length` that is not a safe non-negative integer as absent. No spec change.

### F-5-3: `/config` is cached for the life of the page, so a padding-policy change on the instance makes every later create from an open page fail until it is reloaded
Severity: Low
Location: `client/src/lib/api.ts:185-205` (`getConfig` keeps a successful answer for ever; only a failed fetch is dropped), `client/src/client.ts:53-66`, `client/src/ui/create.ts:97-113` (`pad` with the cached `config.padding`), `client/src/ui/create.ts:192-204` (`400 invalid_blob_length` is shown as "Something went wrong … try again", and trying again reuses the cache)
Violates: SPEC §6.2 ("the policy can change at any time"), §8 ("limits, padding policy and the like apply to the next request without a restart"), conformance item 17 ("`/config` changes whenever the operator changes a setting")
What: Every `createSecret` and every submit of the create page pads with the policy read when the page loaded. After the operator switches `padding_mode`, raises `padding_min` or edits the ladder, the server refuses the blob length (`invalid_blob_length`) and the client's retry sends the same length again. `client/README.md` documents the lifetime ("kept for the life of the page or process") but the create page offers no way out short of a reload, and a bot using `createSecret` never recovers. Nothing is leaked; this is availability and a confusing failure, but it is the client contradicting the live-apply promise the admin panel makes.
Reproduction: `review_r2_pass5.test.ts`, "F-5-3: a padding policy changed on the instance is never re-read, so every later create from the same page fails": after one successful create the instance switches to a bucket ladder; three further `createSecret` calls all fail with `400 invalid_blob_length` and `/config` is never fetched again.
Fix: on a `400` with `invalid_blob_length` (or `files_disabled`) drop the cached entry for that base and retry once with a fresh `/config`; or give `getConfig` a short TTL (a minute) and export an `invalidateConfig(apiBase)` for callers. No spec change.

### F-5-4: `argon2Url` is not held to the page's origin, in code or in the loader, so a frontend can fetch the KDF module from a third origin without any check
Severity: Low
Location: `client/src/lib/argon2-loader.ts:20` (`fetch(url, { cache: "force-cache" })` for any URL), `client/src/ui/dom.ts:70` (`options.argon2Url` taken as given), `client/src/crypto/argon2.ts:31-34` (`instantiate(module, {})`)
Violates: SPEC §10 ("the module is fetched same-origin"), Principle 10, conformance items 13 and 14 (documented, not enforced)
What: Nothing derived from the seed ever leaves for `argon2Url`: the only request to it is the module `GET`, and the instantiated module has no imports, so a hostile module cannot call out. What it can do is compute a wrong or constant `pass_key`, which silently reduces every passphrase secret made or opened by that frontend to seed-only protection (`KEK_pass = HKDF(seed ‖ constant)`), which an attacker with the link but not the passphrase can then open. The built-in pages are protected by the CSP (`connect-src 'self'`, or `'self'` plus the API origin in subdomain mode), so a cross-origin module fetch is blocked there; a third-party frontend using `wireCreate`/`wireReveal` with `argon2Url: "https://cdn…"` is not, and the README offers no warning beyond the checklist. A one-line check keeps the "by construction" claim honest.
Reproduction: `review_r2_pass5.test.ts`, "F-5-4: loadArgon2 fetches the module from whatever URL it is given, cross-origin included": with `fetch` stubbed, `loadArgon2("https://cdn.example/argon2.wasm")` requests that URL and returns a working `Argon2`.
Fix: in `loadArgon2`, when `location` exists, resolve `url` against `location.href` and refuse (`ShhError("argon2_unavailable", "the Argon2 module must be same-origin")`) when its origin differs from `location.origin`; say so in the README's option list. The `apiBase` option is legitimately cross-origin (`api.` subdomain, D-11) and needs no such check. No spec change.

### F-5-5: Two manifest shapes still decode differently in the Rust core and the TypeScript client (S-46 residual)
Severity: Low
Location: `client/src/crypto/container.ts:129-130` (`Number.isInteger(-0)` is true and `-0 < 0` is false) vs serde_json's `-0` → `F64(-0.0)` refused for `u64` (`crates/shhnote-core/src/container.rs:28,94`); `client/src/crypto/container.ts:44-48` (every duplicate key in an object is refused, unknown keys included) vs serde's unknown fields, which are skipped without duplicate detection (`container.rs:10,23`)
Violates: SPEC §2.14 / Principle 11 (one protocol; "the parsing cases both implementations must refuse identically")
What: S-46 pinned BOM, duplicate known keys, non-integer numbers, lone surrogates, a missing `text` and `null` entries, and those all hold (re-checked, see below). Two cases are not pinned and disagree: `"size": -0` is a 0-byte file in TypeScript and a manifest error in Rust; `{"x":1,"x":2}` next to the real fields is a manifest error in TypeScript and ignored in Rust. The plaintext is authenticated, so only the sender controls this; the effect is a blob that one conforming client opens and the other calls corrupt, which is what §2.14 exists to rule out. (Deep nesting in an ignored key was checked and is accepted by both, to 500 000 levels, without leaving the `ShhError` contract.)
Reproduction: `client/test/review_r2_pass5.test.ts` "F-5-5: a file size of -0 …" and "F-5-5: a duplicated unknown key …", mirrored by `crates/shhnote-core/tests/review_r2_pass5.rs` (`f_5_5_file_size_negative_zero_…`, `f_5_5_duplicated_unknown_key_…`). Both suites pass and show opposite decisions.
Fix: in TypeScript, refuse `-0` (`Object.is(meta.size, -0)`) and refuse duplicate keys only among the keys the schema knows (or, simpler, keep refusing all duplicates and make Rust do the same with `#[serde(deny_unknown_fields)]`, which also refuses unknown keys outright; that is the stricter, more parity-proof choice but rejects manifests a future `v: 1` client might extend). Add both as `reject[]` vectors in `vectors/generate.py` (the README allows regenerating `v1.json` before the first deployed instance). No spec change.

### F-5-6: On the reveal page the `data-shh-max-blob-bytes` attribute wins over the fresher `/config` value, so a tab left open across a raised limit claims a single-view secret and then refuses its body
Severity: Low
Location: `client/src/ui/reveal.ts:36,130` (`pageMaxBlobBytes ?? config.max_blob_bytes`; the attribute is read once at load, `/config` is fetched after the press and discarded for this purpose), `client/src/ui/dom.ts:67-71`, `crates/shhnote-server/templates/base.html:17` (the attribute is the instance's own `max_blob_bytes`)
Violates: SPEC §10 ("refuses a body longer than the instance's `max_blob_bytes`"), D-1 (a claimed secret that its recipient cannot read)
What: The body cap can only be applied after the claim (the length arrives with the headers, after the server's conditional `UPDATE`), so a cap below the real blob size always costs a single-view secret: the page keeps the claim token and retries, but every retry meets the same cap. The attribute and `/config` carry the same number at render time; they diverge when the operator raises `SHH_EXTERNAL_MAX_OBJECT` (or enables an external tier) and restarts while a recipient's `/s` tab is already open, then a secret created at the new size is opened from that tab. `/s` is `no-store`, so a cached page is not a vector; an open tab is. The library (`revealSecret`) uses `/config` unless the caller passes something smaller, which is the right precedence.
Reproduction: code reading of the lines above; `pageSettings` precedence is pinned by `spec_client.test.ts` "options win over the attributes". The claim-before-cap ordering is inherent (`client.ts:121` then `:125`; `reveal.ts:131` then `:154`).
Fix: on the reveal page, use `Math.min(options.maxBlobBytes ?? Infinity, config.max_blob_bytes)` and drop the attribute from the cap (keep it for the create page's early "too large" hint). No spec change.

### F-5-7: Scrubbing residuals: the passphrase bytes handed to WASM are not wiped on the JavaScript side, and the lookup value and claim token survive `pagehide`
Severity: Low
Location: `client/src/crypto/argon2.ts:45,57-63` (`pwd = encoder.encode(passphrase)` is copied into WASM memory, which is wiped; `pwd` itself is not), `client/src/ui/reveal.ts:60-64,72-83` (`lookupValue` and `claimToken` are kept through `pagehide` so a confirm still retrying can finish; neither is cleared afterwards)
Violates: SPEC §10 (best effort; the list of what is overwritten is otherwise exact), round-1 F-5-5 item "`pwd` copy in JS is not wiped", which S-45 did not include
What: `pwd` is one `fill(0)` away; the passphrase string itself cannot be wiped, so this closes only the second copy. `lookupValue` is a server credential (it reveals, confirms or reports the secret) and `claimToken` lets its holder re-download a claimed blob within the window; both stay in the page's heap after the seed has been zeroed. The comment explains why (`reveal.ts:62-63`); the handler could still clear them once the confirm loop has ended, and the confirm loop could copy what it needs. Neither is a promise §10 makes, so this is hardening, not a regression.
Reproduction: code reading of the lines above.
Fix: `pwd.fill(0)` in the `finally` of `Argon2.hash`; in `wireReveal`, wipe `lookupValue` and null `claimToken` on `pagehide` when no confirm is in flight, and have `display()` take its own copy of `lookupValue` for the retries.

### F-5-8: The reveal page shows "couldn't be decrypted" for a rate limit, a drain `503`, a setup-gate `503` and an over-cap body
Severity: Low
Location: `client/src/ui/reveal.ts:166-169` (`e.code === "network" ? … : t("reveal-error-corrupt")`), `client/src/ui/reveal.ts:202-203`
Violates: SPEC §4 (the `429` carries `Retry-After`; the drain `503` and `not_configured` are explicit, retryable states), §10 ("a clear failure"), conformance item 9's spirit
What: Any `ApiError` other than `404` and `network` (`429 rate_limited`, `503` during a drain or before setup, `0 too_large`) lands on "This secret couldn't be decrypted. The link may be incomplete." The link is fine and the secret is not corrupt; a recipient who believes the message asks the sender for a new link, and for a single-view secret the sender's resend is the only way out. A `429` on reveal is the realistic case (shared NAT, Tor). No per-secret fact leaks, since the server's answer was not secret-specific.
Reproduction: code reading; `messageFor` on the create page handles `0`, `413` and the rest separately (`create.ts:192-204`), the reveal page does not.
Fix: map `429` and `503` to a "try again in a moment" string (reuse `reveal-error-network`) and `too_large` to a distinct string; keep "corrupt" for `ShhError` only. No spec change.

## Suspicions

- **`padding_min` has a floor but no ceiling** (`crates/shhnote-core/src/settings.rs:184-186`: `at_least(v, 65536)` only). An admin can set it above `max_blob_bytes`; `/config` then advertises it, every create page allocates `padme(padding_min)` bytes for a one-line note before the "too large" check (`pad` runs before the `max_blob_bytes` comparison, `create.ts:110,121`), and no secret can be created. The operator harms only their own instance, but §7.2 says settings are "range-checked as a whole" and the ladder has exactly this upper check (`≤ SHH_EXTERNAL_MAX_OBJECT`, C3). For pass 4: confirm by `PATCH /api/v1/admin/settings {"padding_min": "1099511627776"}` and then `GET /config`. Client-side mitigation regardless: check `paddedSize(...) > max_blob_bytes` before allocating in `encrypt`/`wireCreate`.
- **`createT` on a block that is literally `null`** throws a `TypeError` on first use (`i18n.ts:53,58`; test "createT falls over on a block whose JSON is null"). The block is written by the server (`ui_json`, `<` escaped) or the frontend author, never by a user, so this is a robustness nit: `typeof strings === "object" && strings !== null` would make it fall back to the key like every other malformed block.
- **bfcache.** `pagehide` wipes `seed` in place and nulls `locked`; a page restored from the back-forward cache (no `unload` handler, so it is eligible) comes back with a zeroed seed and a passphrase form whose submit does nothing (`if (!locked) return`). The URL still carries the fragment, so a reload recovers (the claim token is in `sessionStorage`). On the create page the readouts are blanked but the copy buttons' closures still hold the links, so "Copy" keeps working on a blank result. To confirm: reveal to the passphrase prompt, follow a footer link, press Back, in Firefox and Chromium. A `pageshow` handler with `event.persisted` that reloads or re-arms would settle both.
- **A file-card template without `a[data-shh-file-download]`** throws inside `display()` (`reveal.ts:273`) after the text has been written into `[data-shh-text]` and the fragment scrubbed, so the page returns to "armed", shows "corrupt", keeps the plaintext in the hidden `<pre>`, and never confirms; the claim token stays in `sessionStorage` and the retry meets the same template. The README calls the anchor required, so this is an author error, but failing before touching the DOM (validate the template once at `wireReveal` time) would keep a bad template from consuming a single-view secret.
- **`file.type` is neither sanitised nor bidi-isolated** in the meta line (`reveal.ts:243`: `` `${file.type || "application/octet-stream"} · ${formatSize(...)}` `` as `textContent`). The name is cleaned and wrapped in `<bdi>`; the type is not, so a sender's `type` containing U+202E reverses the rest of the inline run in the built-in fallback card (`<li>` with inline spans), including the "Download" label. Cosmetic; `textContent` means no markup. Running the type through `sanitiseFileName` (or a `<bdi>`) would close it.

## Checked and clean

- **Vectors.** Both suites replay `vectors/v1.json` and pass (baseline log; 9 vectors, 38 `reject[]` cases including the S-48 multi-chunk and truncation negatives and the S-46 parsing cases, plus `reject_fragments[]`). Everything round 1's F-5-8 listed as missing is now a vector; the two gaps in F-5-5 above are the only parity cases found that are not.
- **Fragment** (`fragment.ts`, `fragment.rs`): exactly 44 base64url characters, one optional leading `#`, canonical trailing bits on both sides (`fromBase64Url` and base64's `URL_SAFE_NO_PAD`), kind byte checked after decoding and before any derivation; `0x01`/`0x02` only, other bytes → `unsupported_version`. `parseFragment` takes the first `#`; path and query cannot carry one. `location.hash` is used unchanged on `/s`, `/burn` and `/report`. Kind refusal before derivation holds on every page: `/s` and `revealSecret` refuse a burn fragment, `/burn`, `burnSecret` and the create page's "destroy now" use `"burn"`, `/report` decodes `"share"` so a pasted burn link is "invalid" and the burn token is never sent as a lookup.
- **Key material.** KEKs via `deriveKey`, non-extractable (`kdf.ts:58`); EK generated extractable only for `wrapKey`, unwrapped non-extractable (`secret.ts:38,133`); no `exportKey` anywhere in `client/src`. Raw material in JavaScript is the seed, the Argon2 output (`passKey`, wiped at `secret.ts:70`) and `seed ‖ pass_key` (wiped at `:71`), as §2.4 now says. `localStorage` holds the theme only; `sessionStorage` holds `{claimToken, expiresAt}` under `shh-claim:<base64url(SHA-256(lookup))>` and nothing else (`claims.ts:69-71`; pinned by `spec_client.test.ts` "keeps only the token and its expiry…"); nothing reaches `console` beyond error objects, cookies, IndexedDB, `innerHTML` or `history`.
- **sessionStorage claim token.** The key is the server's own `lookup_key`, which the create request already sends and which cannot be inverted to `lookup`; the stored pair cannot reveal, confirm or burn anything without the seed. Deleted on confirm (`reveal.ts:255`), on `404` (`:163`), on expiry (`get` and `prune`). Per tab, so a second tab gets the uniform `404` as §5.1 intends. Every storage access is in `try/catch` and a throwing storage (Tor Browser, private mode) only loses the reload case (test "delete forgets a claim, and a storage that throws…"). Expiry is client-clock (`Date.now()`), stored first with the 24 h maximum and shortened to the instance's window from the already-cached `/config`; the server's own window (rounded up to the minute, D-18) is the authority and a stale entry just meets the `404`.
- **`fragment_version`.** `createSecret` checks before `encrypt` and before any upload (`client.ts:53-55`); `revealSecret` after parsing the fragment and before `lookup` is derived or any request leaves (`:113-121`); `wireCreate` before encrypting (`create.ts:97-99`); `wireReveal` after the press and before the reveal request (`reveal.ts:123`; `lookup` and the storage key are derived locally first, which sends nothing). An unsupported version leaves the seed in memory and the fragment in the URL, consumes nothing and keeps the button off; `wireCreate`'s `finally` wipes the in-flight seed and burn token. Pinned by `spec_client.test.ts` "protocol version (revision 3, B5)" and "protocol check in the controllers".
- **Where derived material goes.** Every request is to `apiBase` (option, else `data-shh-api`), with `credentials: "omit"` and `cache: "no-store"` (`api.ts:83`). Create sends `SHA-256(lookup)` and `SHA-256(burn_token)` (test "the burn-token hash and lookup hash leave the client…"); reveal, confirm and report send `lookup`; burn sends the raw token (§2.12). `argon2Url` receives only the module `GET` (F-5-4 is about the module, not about data leaving). The share and burn links are built from `location.origin` and put into the DOM as text and one `href` by design.
- **`revealSecret` with `confirm: false`** returns `{payload, singleView: true, claimToken}` and sends no confirm (test "revealSecret with confirm:false returns the token…"); `claimToken` falls back to the one the caller passed, since the server sends no header on a re-download (`api.rs:598-600`). A `claimToken` passed for a TTL secret is routed to `redownload` and gets the uniform `404` (`api.rs:593-602`), which is the server's rule, not a client fault.
- **Failed confirm.** The decrypted payload and the token live on the thrown `ApiError` only (`client.ts:136-139`); on the page, in `shown`, which `pagehide` wipes.
- **Scrubbing, as promised in §10.** Create: file plaintext wiped as soon as `encrypt` returns (`create.ts:119`), seed and burn token in `finally` (`:146`), the decoded burn token after "destroy now" (`:185`); `pagehide` wipes anything in flight, blanks the passphrase field and the link readouts and drops the `href` (`:58-68`). Reveal: `display()` wipes the collected ciphertext (`:211`), `pagehide` wipes seed, ciphertext and file bytes, clears the field, text and list and revokes blob URLs (`:72-83`). `history.replaceState` after a reveal (`:217`), after a `404` (`:164`) and on both burn outcomes (`burn.ts:30,34`); `Referrer-Policy: no-referrer` on every response and fragments are never part of `Referer` anyway. `performance.getEntriesByType("navigation")[0].name` keeps the original URL with its fragment, but only same-origin script can read it, and such script could read `location.hash` before the scrub regardless. Only `tabs.ts` writes a hash to history, on admin pages. The `data-shh-keep-hash` language links copy the fragment into their `href` on click, before any reveal, which is the intended language switch.
- **Streaming decoder.** `openStream` holds back one unit and opens the final chunk with the last flag; a body cut mid-chunk, ending on a boundary without a last chunk, or shorter than a tag fails (`stream.ts:70-77`; `spec_client.test.ts` "fails like the one-shot path when the stream ends early"). `display()` runs only after `decryptBody` has finished, so a failure at chunk *i* puts nothing in the DOM. Each plaintext chunk is wiped after `push` and the manifest bytes after parsing. The passphrase path collects the body (`reveal.ts:147`), bounded by the cap (F-5-1/F-5-2 are about what the cap is). The decoder never allocates more than the length prefix allows (`stream.ts:110`), which is the bound F-5-1 asks to tighten.
- **Mode detection.** Direct unwrap first, then the prompt; retries are local, one Argon2 run per submit, bounded by §2.9; no loop. Argon2 parameters are bounds-checked in `parseHeader`, again in `Argon2.hash` and a third time in WASM, before any allocation.
- **Argon2 module.** `instantiate(module, {})`: no imports, so the module cannot call out. Fetched on load of `/` and `/s` whether or not a passphrase is involved (D-22). WebAssembly missing or blocked → `argon2_unavailable` and the specific message; nothing weaker is ever used. S-44: work memory is caller-owned and `zeroize`d in both the WASM crate (`argon2-wasm/src/lib.rs:61-64`) and the core (`kdf.rs:76-79`); pinned by `spec_client.test.ts` "work memory is wiped before the WASM call returns".
- **Caller templates.** `fromTemplate` clones the first element of `<template data-shh-template=…>`; every string the controllers insert goes through `textContent` (names, sizes, types, status text, link labels) and the name additionally through `sanitiseFileName` and a `<bdi>` built with `createElement`; `innerHTML` and `insertAdjacentHTML` do not occur in `client/src`. The download anchor gets an `application/octet-stream` blob URL and a sanitised `download` name whatever the template says. Dropzone items show the chooser's own file names, as text.
- **`createT`.** Reads the `<script type="application/json" data-shh-i18n>` block that the server renders from Fluent with `<` escaped (`web.rs:371-377`), so a translation cannot close the block; `JSON.parse` yields own properties only, so a `__proto__` key is inert; missing block, invalid JSON or missing key fall back to the key. Only the `null` literal case in Suspicions misbehaves. Variables are substituted by plain `replaceAll` into text that is set with `textContent`.
- **Controller options and precedence.** `pageSettings`: option, else the attribute on the root, an ancestor or `<body>`; an unparsable or non-positive `data-shh-max-blob-bytes` is treated as absent; no API base is an error, never a guess; `argon2Url` defaults to `/static/argon2.wasm?v=…` only when the page names an asset version, else `/argon2.wasm`. Pinned by `spec_client.test.ts` "controller options (revision 3, B2)". `wireBurn`/`wireReport` use `apiBase` only.
- **CSP.** `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; font-src 'self'; img-src 'self' data: blob:; connect-src 'self'[ <api origin>]; form-action 'self'; base-uri 'none'; frame-ancestors 'none'` (`web.rs:741-744`), no `'unsafe-inline'`/`'unsafe-eval'`; instantiation via `compileStreaming` + `instantiate` needs exactly `'wasm-unsafe-eval'`; `argon2.wasm` is served as `application/wasm` (`web.rs:846`). No `eval`, `Function`, inline handlers or `style=` in `client/src` or the templates read.
- **Rust/TypeScript parity beyond the manifest.** Header offsets and bounds, `padme`, `blobLen`, `chunkCount`, nonce layout, the order/last-flag/truncation rules, `payload_len` bounds, `manifest_len` bounds, size-sum checks, UTF-8 (`fatal: true` vs serde), BOM, duplicate known keys, non-integer numbers, lone surrogates, missing `text`, `null` entries and the empty passphrase all agree (vectors plus `spec_client.test.ts`, `review_r2_pass5*`). Deep nesting in an ignored key is accepted by both to 500 000 levels and stays inside the `ShhError`/`Error::Manifest` contract. `pad` refuses payloads above `u32::MAX` on both sides.
- **TypeScript rules (S-49).** `erasableSyntaxOnly` is on; no parameter properties, enums, namespaces or decorators in `client/src`; every import has a `.ts` extension; `npm test` runs the sources under Node's type stripping.
- **Trusted activation.** The reveal button reacts to a trusted `click` with `detail > 0` or a trusted Enter/Space `keydown`, only while `navigator.userActivation.isActive` (`activation.ts`); the form's `submit` is always prevented; the burn and report forms require `isTrusted` on `submit` (a scripted `requestSubmit()` would pass there, which §5.1 only forbids for the reveal). Nothing is fetched on load except the Argon2 module.
