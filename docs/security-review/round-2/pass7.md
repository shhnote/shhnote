## Findings

### F-7-1: A create dropped while the object store acknowledges the PUT leaves an object nobody counts; the ceiling is then exceeded by the next honest create
Severity: Medium
Location: `crates/shhnote-server/src/api.rs:480-492` (the `OrphanGuard` is armed only after `storage.put` returns), `crates/shhnote-server/src/storage.rs:596-613` (`S3::put`), `storage.rs:439-444` (`Local::put`, the rename runs on the blocking pool and completes even when the future is dropped), `storage.rs:239-245` (a dropped `Reservation` gives its bytes back)
Violates: D-20, SPEC §6.1 ("They count every object the tier holds, parked deletes included"; "the guard removes it if the request is cancelled before the row is written" is the code's own claim at `api.rs:486-487`), Principle 7
What: When the client connection goes away between the moment the object store has committed the object and the moment the handler polls the response, hyper drops the handler future at the `put` await. The `Reservation` is dropped (bytes returned to the ledger), no `OrphanGuard` exists yet, and no row is written, so the object sits in the tier uncounted until the next restart's orphan sweep. For S3 the window is the store's commit-to-response latency on every upload; for local disk it is the `rename`. Each hit costs the attacker one upload and gains one uncounted object of up to `SHH_EXTERNAL_MAX_OBJECT`; repeated, the disk or bucket grows past `SHH_LOCAL_MAX_TOTAL_BYTES` / `SHH_S3_MAX_TOTAL_BYTES` until someone restarts the server. Round 1's `spec_disconnect_after_upload_leaves_no_uncounted_object` observed the same (`zombies` is computed and then discarded) and only asserts that a restart cleans up.
Reproduction: `r2_h_request_dropped_during_put_leaves_uncounted_object_and_breaks_ceiling` — an in-memory S3 that stores the object and answers the PUT 400 ms later; the create is aborted once the object is in the bucket. Observed: `tier holds 131199 bytes, rows account for 0`; `SHH_S3_MAX_TOTAL_BYTES` = one object; the next honest create answers `201` and the bucket holds `262398` bytes (2× the ceiling) while `Blobs::reserve` still has room.
Fix: arm the guard (and keep the reservation) before `put`, not after: create `OrphanGuard { key }` right after `Blobs::new_key()`, so a drop at any later await deletes the object; move `reservation.commit()`/drop semantics accordingly (a dropped reservation after a committed put must be converted into `release_stored` after the guard's delete, or simply keep the reservation alive in the guard until the delete has run). No spec revision needed. Alternatively, run the orphan sweep periodically from the scheduler, not only at startup.

### F-7-2: Trickling uploads hold every upload slot for the whole upload deadline (36 h at the 4 GiB maximum)
Severity: Medium
Location: `crates/shhnote-server/src/api.rs:286-309` (`BODY_IDLE_TIMEOUT` 30 s per chunk, `upload_deadline` = max(60 s, `max_blob_bytes` / 32 KiB)), `api.rs:318-323` (the permit is taken before the body is read and held to the end), `api.rs:757-764` (only the per-chunk idle timeout and the overall deadline are enforced, never a rate)
Violates: SPEC §7.1 ("The server applies header, idle and request timeouts and the concurrent-upload cap" — the cap becomes the attack surface), Principle 7 (operator-side availability of creates is not bounded by anything the attacker pays for)
What: The comment at `api.rs:288` says "the whole upload must finish at this rate or better", but 32 KiB/s is only used to compute a far-off total deadline. A client that sends one byte every 29 s satisfies the idle timeout, so `SHH_MAX_UPLOADS` (default 64) connections, each sending a few bytes a minute, hold every permit until the deadline: 64 s on an inline-only instance, 36 h on one with `SHH_EXTERNAL_MAX_OBJECT` at 4 GiB. Every other `POST /secrets` answers `503 too_busy` meanwhile. The create rate limit (30/h per IP) means three IPv4 addresses or three IPv6 /64s suffice.
Reproduction: `r2_h_trickle_uploads_hold_every_slot` — `SHH_MAX_UPLOADS=2`, two multipart bodies whose blob part arrives one byte every 40 ms, then an honest create: `503 {"error":{"code":"too_busy",…}}`.
Fix: enforce a rolling minimum rate: in `next_chunk`, bound each wait by the time the bytes already received would allow at the minimum rate (e.g. deadline = start + received/32 KiB + a small grace), or shrink `BODY_IDLE_TIMEOUT` as the upload stalls; also take the upload permit only once `meta` has been validated and the first blob chunk has arrived. No spec revision needed.

### F-7-3: Before setup, any unknown path under `/{locale}/admin/` renders the public 404 page with the site chrome instead of the setup 503
Severity: Low
Location: `crates/shhnote-server/src/app.rs:121-125` (the gate opens everything whose path starts with `/{locale}/admin/`), `crates/shhnote-server/src/web.rs:219-244` (the `/admin` nest has no fallback, so unmatched admin paths fall through to `pages()`' `not_found`, the public error page)
Violates: D-29 ("every route but the admin panel, the admin API, `/static/*` and `/health` answers `503` … a setup page for pages"), Principle 12
What: `is_admin_path` matches the prefix, not the panel's routes. `/en/admin/nothing-here`, and dot-segment paths nobody normalises such as `/en/admin/../s`, pass the gate, miss every admin route and are answered by the website's 404 template: full navigation (links to create, how-it-works, policy pages) and the footer with the version. Nothing secret leaks, but an unconfigured instance shows a public page it is supposed to hide.
Reproduction: `r2_r_setup_gate_blocks_everything_public_and_never_rearms` — on an unconfigured instance `GET /en/admin/nothing-here` → `404` with `<!doctype html>…` (the public error page), expected `503`.
Fix: give the admin routers a fallback that answers like the panel (a bare 404 or a redirect to the login page), or make the gate match the panel's exact routes. No spec revision needed.

### F-7-4: In `SHH_WEB=api` mode a redirect is served for every path with a trailing slash
Severity: Low
Location: `crates/shhnote-server/src/app.rs:179-199` (`redirect_trailing_slash` runs before routing on every host and mode), `app.rs:82`
Violates: D-24 / SPEC §7.1 ("In `api` mode the locale redirect and every public page return `404`"), SPEC §11 ("In `SHH_WEB=api` mode no public page is served")
What: `/en/`, `/s/`, `/anything/` answer `308` with `Location: /en` etc. on an api-mode instance (and on the admin subdomain for non-panel paths). The redirect discloses nothing, but it is a public response the spec says must be a 404, and it lets a scanner tell an api-mode shhnote from a dead host. The same layer also normalises `//evil.com/` to `/evil.com` (fine).
Reproduction: `r2_s_api_mode_serves_no_redirect` — `GET /en/` on `SHH_WEB=api` → `308 Location: /en`, expected `404`.
Fix: in `redirect_trailing_slash`, skip paths that are not API or admin paths when `config.web == WebMode::Api` (or apply the redirect only to `/api/*` and `/{locale}/admin/*` in that mode). No spec revision needed.

### F-7-5: `init --env` appends a second `SHH_SECRET_KEY` line when the set one is written as `export KEY=…` or `KEY = …`, and the server reads the new one
Severity: Low
Location: `crates/shhnote-server/src/init.rs:52-67` (only `KEY=` at line start, after whitespace, counts as set), `crates/shhnote-core/src/config.rs:658-666` (`read_dotenv` collects dotenvy's pairs into a `HashMap`, so the last line wins; dotenvy 0.15.7 accepts `export KEY=value` and whitespace around `=`)
Violates: SPEC §8 ("never overwriting a set value"), D-9 (the token the operator set is silently replaced), Principle 12
What: dotenvy and `init` disagree on what a set key looks like. For the two forms dotenvy accepts but `init` does not recognise, `init` appends a fresh `SHH_SECRET_KEY=` (and `SHH_ADMIN_TOKEN=`) line; the server then signs sessions with the appended key and accepts the appended bootstrap token, while the operator still believes the values they wrote are in force (and may have shared the old token with a colleague). Running `init --env` again appends nothing (the plain line now exists), so the duplicate is permanent.
Reproduction: `r2_x_init_env_never_changes_what_the_server_reads` — `.env` with `export SHH_SECRET_KEY=short-set-value`: `shhnote check` before init fails with "SHH_SECRET_KEY is invalid: must be at least 32 characters"; after `shhnote init --env .env` the file has two `SHH_SECRET_KEY` lines and `shhnote check` prints `ok`, i.e. the server now reads the appended value. Same for `SHH_SECRET_KEY = short-set-value`. The plain form is kept correctly.
Fix: parse the line the way dotenvy does (strip a leading `export `, allow whitespace around `=`) when deciding "set", and refuse to append when any line already names the key in any form. No spec revision needed.

### F-7-6: `init --env` writes the secrets into a world-readable file without a word
Severity: Low
Location: `crates/shhnote-server/src/init.rs:116-124` (the temp file is created `0600` and then `set_permissions(meta.permissions())` copies the old mode)
Violates: Principle 12 (secure by default); SPEC §8 asks for "keeping its permissions", so the wording needs a revision if the mode is to be tightened rather than warned about
What: An example env file copied into place as `0644` keeps `0644` after `init` fills `SHH_SECRET_KEY` and `SHH_ADMIN_TOKEN` into it. Nothing in the output says so. Every other user on the host can read the key that signs admin sessions and the bootstrap token.
Reproduction: `r2_x_init_env_does_not_leave_secrets_world_readable` — `.env` at mode 644 with `SHH_SECRET_KEY=`; after `init --env` the file is still `644` and holds the key; stdout/stderr contain no warning.
Fix: either tighten the new file to `0600` when the old mode grants group/other read (and say so), or at least print a warning naming the mode. The first option contradicts "keeping its permissions" in SPEC §8 and needs a one-line spec revision; the warning does not.

### F-7-7: The test harness leaks one SQLite database per test per process and filled `/tmp`
Severity: Low
Location: `crates/shhnote-store/src/lib.rs:210-217` (`sqlite_path_for_tests` names files `<name>-<pid>.db` and removes only a same-named file of the same pid; nothing ever deletes them)
Violates: CLAUDE.md "Test: `cargo test`" (the suite must be runnable repeatedly); not a product issue
What: Every test process leaves its databases (and `-wal` files) under `$TMPDIR/shhnote-tests`; 13,622 files, 4.3 GB were there at the start of this pass, which made the baseline run fail with SQLite error 13 in `spec_report_answer_is_identical_for_every_target`. `crates/shhnote-server/tests/*.rs` also leave `shhnote-spec-*` directories behind on some paths.
Reproduction: `ls /tmp/shhnote-tests | wc -l` after a few runs; the baseline log's SQLite "database or disk is full".
Fix: name the file by test name only (no pid) so reruns overwrite, and remove the file in a drop guard or at the end of each helper; or point `sqlite_path_for_tests` at `target/tmp`. No spec involvement.

## Suspicions

- **Report timing on large inline rows.** `/reports` runs the same statements whatever the outcome (SPEC §4), but a report that matches deletes a row of `blob_len(bucket)` bytes under `secure_delete = ON`. `r2_c_report_timing_live_vs_missing_measured` (1 MiB inline rows, in-process, 12 samples each) measured medians of 1.48 ms (secret existed) vs 0.62 ms (nothing matched). Whether this survives a network path is unmeasured, and the party who can measure it (a link holder) learns only "it was still active when I destroyed it", which the same party could learn by revealing first. Confirm: measure over loopback HTTP with `SHH_INLINE_MAX` at 64 MiB; clear: show the gap vanishes at 64 KiB buckets or is below jitter over a network. If confirmed it is a Low under §4 "after the same work" and the fix (a constant-cost delete, e.g. parking inline rows for the scrubber too) would be a design change.
- **SQLite write lock held across object-store I/O on the single-view claim.** `api.rs:609-618` keeps the `begin_claim` transaction (which has already written, so it holds the SQLite reserved lock) open while `open_blob` talks to S3 (connect 10 s + response 10 s). Every other writer waits up to `busy_timeout` = 5 s and then fails with "database is locked" (a 500). An attacker cannot slow S3, so this needs a slow store to matter; confirm by pointing the `fake_s3` hang harness in `spec_resources.rs` at a claim and timing a concurrent create.
- **Transient spool overshoot.** `api.rs:417-421` writes the chunk to the spool before checking `written > cap`, so a spool can exceed its reservation by one body chunk (hyper's read buffer, up to ~400 KiB) before the request is refused and the file removed. Bounded by `SHH_MAX_UPLOADS` × chunk; `r2_v_invalid_declared_lengths_never_touch_disk` saw ≤ 4 KiB over with the in-process harness. Confirm with a real socket sending the whole body in one write.
- **`padding_min` above the instance's largest blob is accepted.** `check_blob_limit` only guards the bucket ladder; a `PATCH {"padding_min": 4294967296}` is stored and every create then fails with `invalid_blob_length` until the admin notices. Operator foot-gun only (an admin can already set `rate_create_per_hour` to 1); would be Low hardening under §6.2.
