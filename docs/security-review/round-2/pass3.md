## Findings

### F-3-1: `max_blob_bytes` is a bucket on the server and a blob length in the client, so the advertised maximum is unreachable or unreadable
Severity: Low
Location: crates/shhnote-server/src/api.rs:151 (body limit `max_blob_bytes + 16 KiB`), :340-359 and :442 (checks against `blob_len(max)` and `bucket > max`), :666-677 (`Content-Length = blob_len(bucket)`); client/src/client.ts:62, client/src/lib/api.ts:148 (caps on `max_blob_bytes` as a byte count); crates/shhnote-core/src/padding.rs:98-102
Violates: SPEC §4 (`max_blob_bytes` in `/config`; "the blob must be a valid padded size between the declared length and 16 KiB below it"), §6.1 / `file-uploads` skill ("`bucket ≤ external_max_object` → the external tier"), §10 ("refuses a body longer than the instance's `max_blob_bytes`"), D-1 (a claimed single-view secret that cannot be read is destroyed unread)
What: The server treats `SHH_EXTERNAL_MAX_OBJECT` (and `/config`'s `max_blob_bytes`) as the largest *bucket*: `bucket > max` is refused, and a blob at the top bucket is `blob_len(max) = max + 95 + 16·⌈max/65536⌉` bytes. Two things follow. (1) The route's body limit is `max + 16 KiB`, which the 95-byte header plus the per-chunk tags exceed from 1019 chunks on, so with the default 64 MiB cap the top bucket's blob is 413 `too_large` before any framing is counted: the instance advertises a maximum it cannot accept. (2) Below that point (any cap under about 63 MiB) the server stores the top bucket and serves it with a `Content-Length` above `max_blob_bytes`, while the reference client refuses to upload (`client.ts:62`) or read (`api.ts:148`, `too_large`) anything longer than `max_blob_bytes`. A third-party client that follows §6.1 and pads to the top bucket therefore creates a secret the built-in reveal page claims (the header check runs after the server has committed the claim) and then refuses; retrying with the kept claim token repeats the refusal, so a single-view secret is consumed unread. No secret content or metadata leaks; the cost is one unreadable secret per occurrence and a confusing limit.
Reproduction: `review_r2_pass3_top_bucket_of_default_external_tier_is_unreachable` (local tier, default 64 MiB cap: a blob of `blob_len(64 MiB)` is 413 `too_large`; `blob_len(64 MiB) = 67 125 343 > 67 125 248`); `review_r2_pass3_server_serves_blobs_longer_than_advertised_max_blob_bytes` (cap 1 MiB: the top bucket is 201 Created and served as 1 048 927 bytes against an advertised 1 048 576); core test `review_r2_pass3_top_bucket_exceeds_the_framing_slack_from_64_mib` (the first failing bucket is 1019 × 65 536).
Fix: Decide what `max_blob_bytes` means and apply it on both sides; this needs a one-line spec clarification. The least disruptive reading is "largest padded size (bucket)": make the body limit `blob_len(max_blob_bytes) + FRAMING_SLACK`, and have the client compare the bucket (`encrypted.bucket`) at create and cap the body at `blob_len(max_blob_bytes)` at reveal (`client.ts:62`, `api.ts:148`, the `Math.min` at `client.ts:124`). Alternatively define it as the largest blob length and make the server refuse `blob_len(bucket) > max` instead of `bucket > max`.

### F-3-2: `shhnote init --env` overrides values set as `export KEY=…` or `KEY = …`
Severity: Low
Location: crates/shhnote-server/src/init.rs:52-67 (`line.trim_start().starts_with("KEY=")`), crates/shhnote-core/src/config.rs:658-666 (dotenvy, last line wins in the `HashMap`)
Violates: SPEC §8 ("never overwriting a set value"); CLAUDE.md ("`init` … `--env <path>` writes them into that file")
What: `apply` recognises a key only as a line beginning with `SHH_SECRET_KEY=` exactly. The `.env` reader (dotenvy 0.15) also accepts `export SHH_SECRET_KEY=value` and `SHH_SECRET_KEY = value`, which are common in hand-written env files. For those lines `init` reports the key as missing, appends a fresh `SHH_SECRET_KEY=<new>` line, and because `read_dotenv` collects lines into a `HashMap` the appended value is the one the server uses. The operator's secret key is replaced (every admin session dies, which is harmless) and, for `SHH_ADMIN_TOKEN`, the bootstrap token the operator knows stops working while `init --env` does not print the one it wrote. The opposite mismatch is safe but misreported: `KEY=""` and `KEY= # comment` are "already set, kept" although dotenvy reads them as empty, and the server then refuses to start.
Reproduction: `review_r2_pass3_init_env_overrides_values_set_with_export_or_spaces` (`.env` with `export SHH_SECRET_KEY=short`: `shhnote check` fails on the short key, `init --env .env` reports "appended", `check` then succeeds, so the appended key won; same for `SHH_SECRET_KEY = short`) and `review_r2_pass3_init_env_keeps_values_dotenvy_reads_as_empty`.
Fix: Parse each line the way dotenvy does before deciding: strip an optional `export` prefix, trim around `=`, and treat a quoted-empty or comment-only value as empty. Simplest is to run `dotenvy::from_path_iter` (already a workspace dependency) over the file and decide from the parsed pairs, then edit the matching line. Refuse (rather than append) when the key is present more than once.

### F-3-3: Before setup, an unknown path under `/{locale}/admin` renders the public 404 page instead of the setup page
Severity: Low
Location: crates/shhnote-server/src/app.rs:121-128 (`is_admin_path` opens the whole `/{locale}/admin/*` subtree), crates/shhnote-server/src/web.rs:241-242 (the pages router's `not_found` fallback also serves the nested `/admin` prefix)
Violates: SPEC D-29 ("every route but the admin panel, the admin API, `/static/*` and `/health` answers 503")
What: The gate opens every path under `/{locale}/admin`, but the panel router has no fallback of its own inside the website router, so `/en/admin/anything` falls through to the website's error page: a full public page (layout, navigation, footer with the version) on an instance that is supposed to show only the setup page. Nothing secret-specific is on that page and it says nothing about the bootstrap token, so the impact is a cosmetic deviation from D-29, not a leak. The same applies to `/{locale}/admin/keys/delete` with GET (405 from the method router) and to `/{locale}/admin/` (308 to `/{locale}/admin`, then the login redirect).
Reproduction: `review_r2_pass3_setup_gate_unknown_admin_path_renders_the_public_error_page` (`/en/s` is 503; `/en/admin/no-such-page` is 404 with `<nav` and `</html>` and without "not set up yet").
Fix: Give the admin routes nested into `pages()` a `fallback(no_page)` like the admin-host variant has (`web.rs:172`), or narrow `is_admin_path` to the panel's actual routes.

### F-3-4: `files_enabled = false` with a ladder that has no rung for a text secret refuses every create
Severity: Low
Location: crates/shhnote-server/src/api.rs:553-559 (`text_only_bucket` returns 0 when `padded_size` is `None`), :341-345 and :447-449; crates/shhnote-core/src/settings.rs:152-279 (no check of the combination)
Violates: SPEC §7.2 ("Every setting is range-checked as a whole"), §6.1 ("`files_enabled` off … makes the API refuse any blob above the padded size of the largest possible text secret"; a text secret must still work)
What: With files off, the accepted maximum is `padded_size(2 × text_max_bytes + 1 KiB)`. In `buckets` mode that is `None` when the top rung is below that size (for the default `text_max_bytes` of 64 KiB anything under 132 096 bytes, so a one-rung 64 KiB ladder), and `text_only_bucket` turns `None` into 0; the cap becomes `blob_len(0) = 111` bytes and every create, text-only ones included, is refused with `files_disabled`. The settings save accepts the combination without a warning, so an operator who sets "text only" on a small-ladder instance silently switches the instance off. Operator-only, no leak.
Reproduction: `review_r2_pass3_files_disabled_with_a_short_ladder_refuses_every_text_secret` (ladder `65536`, `files_enabled=false`: a 64 KiB-bucket blob, the smallest the instance stores, is 400 `files_disabled`).
Fix: In `text_only_bucket` fall back to the ladder's largest rung when no rung fits (`padded_size(...).or_else(|| policy.largest_valid_at_most(u64::MAX))`), or refuse the combination in `save_settings` ("files_enabled=false needs a ladder rung of at least N bytes").

### F-3-5: The admin API's query-string rejection is axum's plain-text 400, not the shared error shape
Severity: Low
Location: crates/shhnote-server/src/admin_api.rs:139 (`Query<StatsQuery>`)
Violates: `api-endpoint` skill (one shared JSON error shape); consistency with `Strict<T>` (admin_api.rs:319-338), which was added for bodies in round 1 (S-26)
What: `GET /api/v1/admin/stats?days=abc` answers `400` with `text/plain` "Failed to deserialize query string…" from axum's `QueryRejection`. Authenticated admins only; nothing is reflected beyond serde's message. Hardening.
Reproduction: `review_r2_pass3_admin_stats_query_rejection_is_not_the_shared_error_shape`.
Fix: Take `Result<Query<StatsQuery>, QueryRejection>` (or `Query<HashMap<String,String>>` and parse `days` by hand) and answer `error_response(400, "invalid_query", …)`.

## Suspicions

- **Orphan sweep across processes sharing one tier.** `collect_orphans` (storage.rs:137-156) deletes every 22-character object no row references. It runs before the listener is bound, so within one process nothing is in flight; but two server processes on one local directory or one S3 bucket (a rolling deploy, or two instances pointed at one bucket by mistake) would have the starting process delete objects the running one has `put` but not yet committed a row for (api.rs:482-495, a window of one `INSERT`). The ledger comment says "one process owns the tier"; the spec does not. To confirm: start a second process against the same tier while a large create is between `put` and `create` and reveal the secret afterwards (uniform 404 with a row left behind). To clear: state the single-process assumption in SPEC §6.1 and the deployment guide, or skip objects younger than the upload deadline.
- **A valid-shaped orphan that cannot be deleted fails startup.** `collect_orphans` propagates the first `delete` error (`storage.rs:149`). Strays are ignored as the spec says, but an object of our own shape that is undeletable (permissions, an S3 policy) stops the server. Operator-controlled; worth a `log_error!` and continue instead.
- **`init --env` with a key present twice** fills or keeps the first occurrence (`init.rs:54`) while dotenvy uses the last. With `SHH_SECRET_KEY=` first and `SHH_SECRET_KEY=abc` later, `init` reports "filled in" but the server keeps using `abc`. Same root cause as F-3-2; confirm by running the F-3-2 test shape with a duplicate line.
- **`ensure_configured` costs one `COUNT(*)` per request until setup is met** (`app.rs:110`, `api.rs:269-274`), `/static/*` included and before any rate limit. An unconfigured instance can be made to run a query per request from anywhere, but the table is tiny and the instance serves nothing else; not pursued.
