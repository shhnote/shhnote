## Findings

### F-2-1: S-12 regression (incomplete fix): S3 response bodies are read with no timeout; a store that sends headers and then stalls hangs startup, the scrubber, and an upload slot forever
Severity: Medium
Location: crates/shhnote-server/src/storage.rs:816-823 (`read_up_to`: `Limited(...).collect().await`, no timer), :807-814 (`read_small`, `read_page`), :570 (`check_versioning` → `read_small`), :667 (`list` → `read_page`), :843-851 (`status_error` → `read_small`), :832-838 (`expect_success`), :612 (`put` → `expect_success`), :646 (`delete` → `expect_success`); crates/shhnote-server/src/api.rs:482-485 (`storage.put` inside `create`, which is exempt from `request_timeout`, app.rs:163-167)
Violates: SPEC §6.1 ("The S3 client applies connect, request and body timeouts"); Principle 7; S-12 (CHANGELOG: "S3 connect/response/body timeouts")
What: Round 1's fix bounds the connect (`CONNECT_TIMEOUT`), the wait for response headers (`RESPONSE_TIMEOUT`/`send_within`) and the frames of a streamed `get`. Every other body read, `read_up_to`, waits without limit. So an endpoint that returns a status line and `Content-Length: 100` and never sends the body hangs: `Blobs::open` (the versioning check runs at every start, so the server never comes up), the listing pages of the startup orphan sweep, every `scrub` pass (its task stops for good; the sweeper task keeps running), and `create` after the PUT, where the handler keeps its `SHH_MAX_UPLOADS` permit, its ceiling `Reservation`, its spool file and the client connection for as long as the store stalls, with no request timeout on the upload path. Reveal is the only caller bounded elsewhere (`request_timeout`, 30 s). Triggering it needs the object store (or something on the path to it) to misbehave, not a remote client, hence Medium, as S-12 was.
Reproduction: `review_r2_pass2_s3_headers_only_body_hangs_open_scrub_and_create` (fake S3 that answers `200` until switched to "500 with a 100-byte body that never comes"). Observed: `after 20s: startup versioning check finished=false, scrub finished=false, create finished=false` (`RESPONSE_TIMEOUT` is 10 s, so a bounded client would have returned).
Fix: wrap `read_up_to`'s `collect()` in `tokio::time::timeout(BODY_IDLE_TIMEOUT, ..)` (or reuse the idle-per-frame adapter from `get`), so every body read is bounded like the streamed one. No spec change.

### F-2-2: Two processes on one external tier (a rolling deploy) destroy each other's work: the new process's startup sweep deletes an object whose row is about to be written, and its spool cleanup removes the old process's in-flight uploads
Severity: Medium
Location: crates/shhnote-server/src/storage.rs:137-156 (`collect_orphans`: refs read first, then the listing, then delete), :425 and :557 (`clear_parts` of `tmp/` and `SHH_SPOOL_PATH` at every open), :40-41 ("One process owns the tier"); crates/shhnote-server/src/api.rs:482-497 (object stored, then the row); crates/shhnote-server/src/main.rs:114-135 (sweep at every start)
Violates: SPEC §6.1 ("an object without a row is garbage, never a secret" is only true inside one process; "At startup the server lists the tier, deletes unreferenced objects"); Principle 6 (a committed secret is destroyed without a terminal transition and without a counter)
What: `create` writes the object first and the row last (SPEC §6.1). A second process starting against the same database and tier reads `external_refs`, lists the bucket (a paged listing can take seconds on a large bucket) and deletes everything of our name shape that was not referenced at the start of the sweep. Any object the first process `put` after the refs were read and whose row it inserts afterwards is deleted; the row then commits and points at nothing. The creator got `201`; the recipient gets the uniform `404` (TTL) or, for single-view, the claim is rolled back by the missing object (S-30) and the row stays active until expiry, so the secret is silently lost. The same `open` also runs `clear_parts`, which unlinks every `*.part` file, including the ones the old process is writing; its `put` then fails on the rename and the upload gets `500 internal`. Nothing in SPEC.md or `docs/deploy/` says the server is single-process; `docs/deploy/fly.md:23` pins one machine because of SQLite, and `stats.rs:76` explicitly considers "two schedulers running at once (a rolling deploy)". With Postgres and S3 a rolling or blue/green deploy is the normal way to run it, and the window is the length of the listing plus the gap between `put` and the insert.
Reproduction: `review_r2_pass2_second_process_startup_destroys_in_flight_objects_and_spools` (storage level, two `Blobs::open` on one local root and one store). Observed: `the new process deleted an object a row was about to reference: left: 1, right: 0`; the row inserts fine afterwards; the old process's second upload fails with `NotFound` on the rename.
Fix: make the sweep skip young objects: only delete an unreferenced object whose modification time (local `mtime`, S3 `LastModified`, both already accepted residuals in §6.1) is older than the longest possible upload (`upload_deadline`, about `max_blob_bytes / 32 KiB` seconds, plus a margin), and re-check `external_refs` after the listing before deleting. For spool files, likewise only remove `*.part` files older than that deadline (an in-flight spool is written continuously). Alternatively state in SPEC §6.1 and the deploy guides that exactly one server process may run against a tier and that deploys must stop the old process before starting the new one. Either needs a spec revision (§6.1 wording).

### F-2-3: The scrubber starves behind 200 persistently failing deletes; every later pending delete waits forever and the ceiling fills with garbage
Severity: Low
Location: crates/shhnote-store/src/secrets.rs:331-350 (`pending_deletes_sized`: `LIMIT $1`, no ordering, no skip); crates/shhnote-server/src/scheduler.rs:52-77 (`scrub`: a failed delete is logged and the row is retried next tick, in the same batch)
Violates: SPEC §5 / §6.1 ("Retry on every pass until it succeeds" is meant per object; here one failing set blocks the others); Principle 7 (parked objects keep counting toward the ceiling, which fills with objects that will never go)
What: Each tick selects the first `SCRUB_BATCH` (200) `pending_delete` rows. SQLite scans the `WITHOUT ROWID` primary key in order, so the selection is the same 200 rows every tick. If 200 objects cannot be deleted (an object replaced by something `remove_file` refuses, a key stored in a shape `object_name` rejects, a bucket policy that denies `DeleteObject` for a prefix, a 5xx that only some keys get), every row that sorts after them is never visited. Their objects stay in the tier, still counted (`external_bytes` sums every row with an `external_ref`), so a tier whose deletes are stuck eventually answers `507` to every large create although nothing live is stored. Reaching 200 permanently failing deletes needs an operational fault, hence Low; but once reached it does not heal, and a restart does not help (the startup sweep only removes unreferenced objects).
Reproduction: `review_r2_pass2_scrubber_starves_behind_200_failing_deletes` (210 parked objects replaced by directories, one deletable object whose key sorts last). Observed after 5 scrub passes: `row pending: true, object on disk: true`.
Fix: visit rows in a rotating order (`ORDER BY lookup_key` with a cursor that starts after the last key of the previous batch and wraps), or keep the keys that failed this tick in memory and `LIMIT` past them, or raise the batch when more than half of a batch failed. On a delete that fails with a permanent error, log once per tick instead of per row. No spec change.

### F-2-4: While only the admin key is missing, the setup gate runs a database query for every unauthenticated request, outside every limit and timeout
Severity: Low
Location: crates/shhnote-server/src/api.rs:78-87 (`ensure_configured`), :269-274 (`is_configured`: `admin_key_count()` once `site_name` and `contact_email` are set); crates/shhnote-server/src/app.rs:86 (the gate is the outermost core layer, outside `request_timeout` at :83 and outside every route's rate limiter), :110 (called first on every request); crates/shhnote-store/src/api_keys.rs:130-135 (`SELECT COUNT(*) ... WHERE scopes = 'admin'`, no index on `scopes`, migration `0004_api_keys.sql`)
Violates: Principle 7; D-29 ("derived while unmet" is read as "per request")
What: The operator reaches this state by logging in with the bootstrap token and saving the two settings before minting an admin key, which the panel allows. From then until the first admin key exists, every request to any public route, pages, API, locale redirect and CORS preflights included, runs the count on a pool connection, with sqlx's default 30 s acquire timeout and no rate limit (the gate runs before routing) and no request timeout (it wraps `request_timeout`). The query is cheap on a small table, but it is the only unauthenticated, unlimited database query in the server, the table is the operator's and scales with their keys, and the comment at api.rs:57-59 ("an unconfigured instance has no traffic to speak of") assumes the instance is not yet public, which it is as soon as it has a DNS name.
Reproduction: `review_r2_pass2_half_configured_gate_queries_per_request`: 30 000 `user` keys, 100 `GET /en`. Observed: `unconfigured 10.2 ms, half-configured 307 ms (preflights 291 ms)`: 3 ms of database time per gated request, zero when the settings are empty.
Fix: cache the negative result for a short period (for example re-derive at most once per second, or only after an admin write: `create_api_key` and the settings save are the only events that can change it, so the admin code can clear a `dirty` flag the gate checks). Also bound the acquire (`ping`'s 2 s pattern) so a busy pool makes the gate answer `503` rather than wait. No spec change.

### F-2-5: The largest advertised bucket cannot be uploaded: the body limit is `max_blob_bytes + 16 KiB`, but a 64 MiB bucket's tags alone are 16 KiB; the client and the server also disagree on what `max_blob_bytes` caps
Severity: Low
Location: crates/shhnote-server/src/api.rs:150-151 (`body_limit = max_blob_bytes + 16 * 1024`), :294 (`FRAMING_SLACK`), :442-444 (`bucket > max_blob_bytes` is the server's rule); crates/shhnote-core/src/padding.rs:98-102 (`blob_len = 95 + bucket + 16 × ceil(bucket / 65536)`); client/src/client.ts:62 and client/src/ui/create.ts:121 (`encrypted.blob.length > config.max_blob_bytes`)
Violates: SPEC §4 (`max_blob_bytes` in `/config` is the instance policy; §6.1: a blob is accepted iff its bucket is valid and at most the per-object cap); §6.2 (the reference ladder ends at `SHH_EXTERNAL_MAX_OBJECT`, so the top rung is advertised and refused)
What: `blob_len(64 MiB) = 67 125 343`, the body limit is `67 125 248`, and the multipart framing adds a few hundred bytes more, so a blob of the default `SHH_EXTERNAL_MAX_OBJECT` (and of `SHH_INLINE_MAX = 64 MiB` without an external tier) is refused with `413` after the server has already accepted its declared length (the declared-length check passes because it compares against `blob_len(max)`, not the body limit). Any bucket above about 62 MiB has the same problem; in `buckets` mode the admin panel accepts a ladder ending exactly at the cap. The reference client never hits it because it treats `max_blob_bytes` as a cap on the blob's length (header and tags included) and stops one Padmé step lower, which is a second reading of the same field; an integrator following `/config` and §6.1 literally pads to the advertised maximum and gets `413`. No security impact: nothing over the cap is ever stored, hence Low.
Reproduction: `review_r2_pass2_largest_advertised_bucket_is_accepted` (local tier, `SHH_EXTERNAL_MAX_OBJECT=67108864`). Observed: `/config` says `max_blob_bytes: 67108864`; a blob of that bucket gets `413 too_large`.
Fix: set the route's body limit to `blob_len(max_blob_bytes) + FRAMING_SLACK` (one line in `v1`), and state in SPEC §4 whether `max_blob_bytes` is a bucket (server) or a blob length (client), then align the client's check with it. Needs a one-line spec clarification.

### F-2-6: A stalled upload holds its declared size against the ceiling for up to `max_blob_bytes / 32 KiB` seconds; sixteen one-byte-per-29-seconds connections from one address keep the external tier at `507` indefinitely
Severity: Low
Location: crates/shhnote-server/src/api.rs:286-309 (`BODY_IDLE_TIMEOUT` 30 s per chunk, `UPLOAD_MIN_BYTES_PER_SEC` 32 KiB, so the deadline for a 64 MiB instance is 2048 s), :398-414 (the reservation of `cap`, the declared length, from the first spilled byte); crates/shhnote-server/src/storage.rs:100-123
Violates: Principle 7 (user-facing limits are best-effort, so this is hardening); D-20 is by design
What: D-20 is implemented exactly: the declared size is held from the spill on, so disk never exceeds the ceiling. The hold is also what a client that sends nothing useful gets for free: with `Content-Length` set to a 64 MiB blob and one byte every 29 s, each connection holds 64 MiB of a ceiling for 34 minutes while sending 70 KiB. A 1 GiB ceiling needs 16 such connections; the create limit (30/h per client) and `SHH_MAX_UPLOADS` (64) both allow that from a single address, and the client can restart each connection when it is cut, so large creates answer `507` for as long as it likes while inline secrets keep working. The same number of connections already gets `too_busy` at 64, so this is a 4× cheaper variant of an accepted property, not a new class. Without a `Content-Length` the reservation is `blob_len(max) + 16 KiB`, so on a tier with less free room than that every chunked upload is refused at the spill regardless of its real size (a design consequence integrators should know: send `Content-Length`).
Reproduction: `review_r2_pass2_stalled_declared_uploads_hold_the_ceiling` (two uploads declaring 450 000 bytes, 128 KiB sent each, ceiling 1 000 000). Observed: a complete 131 KiB create gets `507` while they stall and `201` once they are gone; it passes, since it only records the behaviour.
Fix: hardening only: make the idle allowance proportional to progress (a chunk must arrive within 30 s *and* the running rate must stay above `UPLOAD_MIN_BYTES_PER_SEC` after the first minute), or hold only `bytes_written + one chunk` of the ceiling while a declared upload is behind schedule. Mention `Content-Length` in `docs.md` for the API. No spec change.

## Suspicions

- **A download in flight at SIGTERM is cut after about 5 s.** `drain::track` (drain.rs:64-66) drops its `InFlight` guard when `next.run(req)` returns, which is when the response head is produced; the body of a 64 MiB external blob streams afterwards, so the drain counts it as finished at once, and `serve.rs:62-70` closes the connection `CLOSE_GRACE` (5 s) after the drain. A single-view recipient can re-download with the claim token after the restart (the row stays `claimed`, D-1), a TTL recipient can read again, so nothing is lost; but the claim window keeps running while the server is down. To confirm: serve a 64 MiB local object to a client reading slowly, send the signal, time the close. Not run (needs a large blob under `/tmp` pressure).
- **Every keyed request takes the SQLite write lock.** `limit` (ratelimit.rs:325) and the admin paths call `touch_api_key` on every request with a valid key; the `UPDATE ... WHERE last_used_on <> $2` matches nothing after the first call of the day, but SQLite begins a write transaction for an `UPDATE` before it knows that, so each keyed request briefly contends with the sweep's 200-row batches and with every claim. A `user`-key holder can issue `rate_user_multiplier × reveal_per_hour` of them. To confirm: measure claim latency under 600/h keyed reveals during a 200-row sweep on a slow disk; expected tens of ms, not a failure. Fix if confirmed: read `last_used_on` with the `find_api_key` row (it is already selected) and skip the `UPDATE` when it equals today.
- **`OrphanGuard` spawns its delete.** `api.rs:537-549` removes a freshly stored object from a spawned task. If the runtime is shutting down (the request was aborted by `connections.abort_all()` in `serve.rs:69`), the spawn may never run and the object stays until the next startup sweep, counted by nothing (`stored` is loaded from rows). Bounded by one object per aborted connection per shutdown; the sweep removes it at the next start (unless F-2-2 applies). To confirm: abort an upload between `put` and the row insert during shutdown and list `blobs/` after.

## Checked and clean

- **Ceiling reservation (S-4, S-5).** `reserve` checks and books under one `Mutex` (storage.rs:103-123); `Reservation` is released on every error path by `Drop` (`?` returns, the aborted future, a panic's unwind), committed only after the row insert (api.rs:498-501), given back on the duplicate (`Ok(false)`, api.rs:505-508) and on a failed insert; `shrink_to` keeps `reserved` consistent before `commit`; nothing double-releases (`committed` flag). `review_r2_pass2_reservation_is_released_on_duplicate_and_disconnect`: with room for exactly two objects, a duplicate create (D-21) and an aborted spilled upload leave the second slot free and the third create gets `507`; `external_bytes <= ceiling`. `collect_orphans` resets `stored` to `None` (reloaded from rows on the next reserve) but leaves `reserved` alone, which is right since it runs before serving. `release_stored` is only called after `finish_delete` succeeds.
- **Pre-spool declared-length check (S-5).** `declared_blob_upper` (api.rs:299-304) is `Content-Length − meta bytes`; `too_big(upper − 16 KiB)` refuses when even the smallest possible blob is over the cap or the text-only cap; `largest_blob_len_at_most` picks the longest valid blob in `[upper − 16 KiB, min(upper, max, text_only)]` and refuses with `invalid_blob_length`, `files_disabled` or `413` when none fits (api.rs:364-385), before `next_field("blob")`. While streaming, `written > cap` is a `400` on the first byte over and `too_big(written)` a `413`/`files_disabled`; with a `Content-Length` the body cannot exceed `cap` anyway. After the body, `bucket_for_blob_len` validates the exact length and the fresh settings snapshot re-checks TTL, cap and `files_enabled` (api.rs:433-449). `spec_invalid_declared_length_is_refused_before_spooling` passes. Memory per upload is at most `blob_len(inline_max)` plus one chunk when an external tier exists (api.rs:391-414), and the route's body limit otherwise; `Store::create` clones the inline blob once (secrets.rs:84).
- **Spool hygiene (round-1 item 2, re-run).** `spec_aborted_uploads_leave_no_spool_files`: 100 uploads aborted after spilling (50 by the body ending, 50 by dropping the future) leave 0 files. `Spool::create` opens synchronously with `create_new` and `0600` under the tier's own `0700` directory (storage.rs:335-357), `Spool` and `Spooled` unlink on drop, and `spec_stalled_upload_does_not_block_shutdown` shows the spool of a stalled upload is gone after a bounded shutdown. Startup removes only `*.part` files (storage.rs:323-332; `spec_spool_path_is_not_wiped_recursively`, S-31).
- **Ceiling concurrency (round-1 item 3, re-run).** `spec_concurrent_creates_respect_the_ceiling` (16 creates, room for 2: exactly 2 × `201`, 14 × `507`, disk ≤ ceiling) and `spec_spool_bytes_count_toward_the_ceiling` (4 paused uploads on a full tier: spool + stored ≤ ceiling, all `507`, 0 spool files after) pass on the current code.
- **Claim race (round-1 item 5, re-run).** `spec_fifty_concurrent_reveals_have_one_winner` (inline and local tier: 1 × `200` with `X-Shh-Claim-Token` and a full-length body, 49 byte-identical `404`s) and the store's `exactly_one_concurrent_claim_wins` pass. The claim is still one conditional `UPDATE ... RETURNING` as the first statement of its transaction (secrets.rs:139-150), the object is opened before the commit (api.rs:614-618, S-30; `spec_missing_object_is_the_uniform_negative` passes), WAL + `busy_timeout = 5000` (lib.rs:98-104). Postgres not run.
- **Expiry grid and claim rounding (D-18, S-6).** `review_r2_pass2_expiry_grid_bounds`: for every TTL from 60 s to 14 d (step 7) and eight values of `now`, `now + ttl ≤ expires_at < now + ttl + grid` and `expires_at` is on the grid; at the 14-day cap the row expires at most 15 d − 1 s after creation (the spec's own rounding, D-18, not a breach of D-7); `claim_expires_at` is always in `(now, now + window + 60)`, so a claim window is never empty, since `claim_window_secs ≥ 60` (settings §7.2). The sweep predicates are the exact complements of the read predicates (`<=` vs `>`, secrets.rs:141, 168, 208, 257, 263), so a row is never both servable and sweepable, and a claim made just before `expires_at` survives as `claimed` until its window lapses (`expired` sweep requires `status = 'active'`).
- **Reports as a daily counter (S-8, S-16, D-19).** `report` runs `count(+1)`, `destroy`, `count(removed, n)` in one transaction whatever the input (secrets.rs:241-250); `review_r2_pass2_fifty_concurrent_reports_count_fifty`: 50 concurrent reports (one matching) all answer `200`, `reports = 50`, `removed = 1`, `active = 0`, no busy errors. Counters are `BIGINT`/`INTEGER` i64 and only ever add small integers; roll-up sums i64 per year (stats.rs:113-121) and would need ~9 × 10¹⁸ events to overflow. No per-report row exists (`migrations/` has no reports table).
- **`last_used_on` (S-7, D-23).** Written as 00:00 UTC of the day, only when it differs (api_keys.rs:77-88); `review_r2_pass2_last_used_on_is_the_day_and_idempotent`: two touches on one day leave the day value; two requests racing on a day boundary both write their own day and the later one wins, which is still a day. Write amplification is one row update per key per day plus the no-op `UPDATE` noted under Suspicions.
- **Orphan sweep rules.** `collect_orphans` deletes only keys that pass `object_name` (exactly `blobs/` + 22 base64url characters, storage.rs:252-269) and are unreferenced by any row, `pending_delete` rows included (`external_refs` selects every non-null ref, secrets.rs:354-361); directories are listed with a trailing `/` and so never match; stray files are counted and left (`spec_orphan_sweep_ignores_stray_files`, `spec_orphan_sweep_on_s3_follows_pages_and_ignores_strays` pass). An object whose row is `pending_delete` is left for the scrubber. The listing holds every key in memory (storage.rs:650-677, 1000 per page, 1 MiB per page body): bounded by the ceiling (`max_total_bytes / 64 KiB` objects at most, ~100 MB of keys per 100 GiB of ceiling); a slow listing delays startup, which is the operator's own store. Startup never fails over a stray entry. Single-process only: see F-2-2.
- **Setup gate.** Once met the gate is an atomic load (api.rs:67-69, 79-81) and never re-arms; `/health`, `/static/*`, `/{locale}/admin*`, the `admin.` host and `/v1/admin*` on the API host stay open (app.rs:121-125) and nothing else does, in both routing modes and in `SHH_WEB=api` (the gate wraps the same core router). The 503 for the API is the error envelope with `no-store`, for pages the setup template (web.rs:98-125), both inside the security-headers layer (app.rs:20-28, 32-37). `review_r2_pass2_half_configured_gate_queries_per_request` also confirms the 503 on `GET /en` and on a CORS preflight while unmet. The per-request query while half-configured is F-2-4.
- **CORS (D-26).** The middleware wraps the API router only (app.rs:64-66): a preflight is answered from `settings.load()` with no database work and no rate limit (`limit` is a per-route layer below it), `204` with fixed allow-methods/headers, `Access-Control-Allow-Origin` only for the site origin or an `allowed_origins` entry, never `*`, never credentials, `Vary: Origin` always (app.rs:221-252). An `OPTIONS` body is never read: `review_r2_pass2_preflight_with_a_huge_body_is_answered_at_once` sends a preflight announcing a 50 MB body over a real socket and gets the `204` (with the §11 headers and `no-store`) at once, after which hyper closes the connection rather than draining the body, so a large preflight body costs nothing. The answer also carries axum's `Allow: POST` for the route, which is harmless. Gated like everything else while unconfigured.
- **Timeouts and the upload cap (S-2) on every path.** `serve.rs:52-55` sets the header read timeout on the hyper builder for every connection; `request_timeout` (30 s) wraps every non-upload route in both web modes and both routing modes (app.rs:82-83, inside `route_by_host`); uploads are bounded per chunk (30 s) and overall (`upload_deadline`), and `SHH_MAX_UPLOADS` is taken with `try_acquire_owned` before the first byte (api.rs:318-322), so a saturated instance answers `503 too_busy` with `Retry-After: 60` instead of queueing. `spec_stalled_clients_are_timed_out` passes. The gate itself runs outside `request_timeout` (F-2-4).
- **Drain 503.** `track` refuses new requests with `503`, `Connection: close` and `Cache-Control: no-store` once stopping (drain.rs:55-63), inside the headers layer (app.rs:25-28), so it carries the §11 headers; in-flight uploads keep their `InFlight` guard for the whole body (the guard lives across `next.run`), the drain waits up to 30 s for them, then 5 s for connections to close, then aborts the tasks, which drops spools (`spec_stalled_upload_does_not_block_shutdown`). A half-received blob is never committed (the row is written after the body is complete and validated). The claim window is database state and survives the restart; see Suspicions for a download in flight.
- **Scheduler.** Two tasks on one 60 s interval (scheduler.rs:15-47): sweep and roll-up never wait on the object store; the scrubber takes 200 rows per tick and deletes the object before the row (scheduler.rs:69-77). The sweep works in batches of 200, one transaction each with its counter (secrets.rs:280-302), then checkpoints the WAL. Ticks of one task never overlap (`interval.tick()` in a loop). The scrubber's ordering is F-2-3.
- **`shhnote init` (§8).** `--env` writes through a `.<name>.<random>.tmp` file in the target's directory, `create_new` + `0600`, `sync_all`, the old file's mode (and owner where allowed) copied, `rename`, directory fsync best effort, and the temp file removed on any failure (init.rs:82-136; unit tests `rewrites_through_a_temp_file`, `a_failed_write_leaves_the_file_alone`, `spec_init` pass). A set value is never overwritten; only an empty `KEY=` is filled; the values are printed only in the no-argument form, and `--env` prints key names and outcomes. Two concurrent `init --env` runs on one file each generate their own values and the last `rename` wins; the file is always whole and self-consistent, but the loser's printed "filled in" refers to values that are not in the file (harmless: the values are read from the file, not the output). A dangling symlink at the path is replaced by a regular file (`canonicalize` fails with `NotFound`, init.rs:83-86), which is the only case where "a symlinked env file is updated where it points" does not hold. No finding.
- **Version in `/config`, `/health`, footer (D-27).** A `&'static str` from `env!("CARGO_PKG_VERSION")` (api.rs:36); nothing per instance or per request.
- **Padding and length math (round-1 item 11).** `padme`, `blob_len`, `bucket_for_blob_len` and `largest_blob_len_at_most` use checked or saturating arithmetic (padding.rs:54-102; round 1's F-2-13 is fixed); `bucket_for_blob_len` rejects a 0 bucket and a chunk count that disagrees with the length. The off-by-tags at the top of the range is F-2-5.
- **Client package, as far as it touches this pass.** `createSecret`/`revealSecret` fetch `/config` first and refuse an unknown `fragment_version` before deriving or sending anything (client.ts:15-20, 53, 116); the claim token lives in `sessionStorage` under a per-lookup key with an `expiresAt`, is pruned when the window closes and read only while it is open (claims.ts), so a reload within the window re-downloads (§5.1) and a stale token is never sent; the body cap defaults to `/config`'s `max_blob_bytes` (client.ts:118-124). `npm test` 64/64 in the baseline. Deeper client review is pass 5's.
