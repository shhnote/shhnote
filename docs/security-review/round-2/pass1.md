## Findings

### F-1-1: `POST /secrets` still tells a hash holder whether the row exists, by the work it does (residual of S-9)
Severity: Medium
Location: crates/shhnote-server/src/api.rs:463-471 (`Ok(_) => Ok(StatusCode::CREATED)` for both outcomes); crates/shhnote-store/src/secrets.rs:74-102 (`create`: on a unique violation the function returns before the `created` upsert and the commit)
Violates: SPEC §4 ("after the same work") read with D-21 ("a distinguishable duplicate response is an existence oracle for anyone holding a hash"); Principle 5
What: Round 1's S-9 fix made the *answer* to a duplicate `lookup_key` or `burn_key` identical to a success (201, empty body, no write). The *work* still differs: a fresh create writes the row, runs the `stats_daily` upsert and commits; a duplicate fails on the unique index inside the transaction and rolls back. In-process on SQLite the medians are 27 % apart at 64 KiB and 19 % apart at 1 MiB (an absolute gap of roughly 0.2–0.8 ms that grows with the blob the attacker chooses, up to `SHH_INLINE_MAX`). Someone holding `SHA-256(lookup)` or `SHA-256(burn_token)` from a dump can therefore probe `POST /secrets` and tell, from timing, whether the victim's row is still there; the first "slow" probe both marks the moment the secret was consumed or destroyed and plants the attacker's row under the victim's link (the re-plant primitive S-9 described, no longer blind). Practical limits: the oracle needs a hash (dump access), yields one transition sample per secret (after the plant every probe is a duplicate again), and is bounded by `rate_create_per_hour` (30/h anonymous, ×10 with a `user` key), so remotely it is a weak signal; on a local or same-datacenter path it is clear.
Reproduction: `crates/shhnote-server/tests/review_r2_pass1.rs::review_r2_pass1_reproduces_duplicate_create_timing_gap` (debug build, SQLite, in-process, 120 interleaved samples at 64 KiB and 16 at 1 MiB):
```
create fresh (64 KiB inline)       p10=751us p50=821us p90=961us
create dup lookup_key (64 KiB)     p10=558us p50=597us p90=665us
create dup burn_key (64 KiB)       p10=491us p50=530us p90=595us
create fresh (1024 KiB inline)     p10=4091us p50=4352us p90=5637us
create dup lookup_key (1024 KiB)   p10=3254us p50=3518us p90=4104us
create dup burn_key (1024 KiB)     p10=2724us p50=2835us p90=3321us
```
(At 64 KiB the duplicate p90 is below the fresh p10; the responses are byte-identical in every sample.)
Fix: either make the duplicate path do the same statements (run the `created` upsert with `+0` and commit instead of rolling back, which removes the upsert-and-commit half of the gap; the row-write half can only be matched by writing and discarding comparable bytes in the same transaction, which is a hack worth weighing against the threat), or record the timing residual under D-21 in SPEC §4 with the rate limit and the one-sample limit as the reasons it is accepted. Either way this needs a spec decision; the code matches the spec's words today.

## Suspicions

- **Setup page under `SHH_ADMIN_ROUTING=subdomain` links to the wrong host.** Confirmed, but a functional bug rather than a leak, so not a finding of this pass (pass 4 territory). `templates/setup.html` uses `ctx.admin_href("/login")`, which in subdomain mode is `/en/login` relative to the *main* host (web.rs:265-267, 315-317); that host does not serve the panel, so the button leads back to the setup page (503) while unconfigured and to a 404 afterwards. `review_r2_pass1_admin_path_form_is_an_ordinary_404_in_subdomain_mode` prints the link and the answer (`/en/login` → 503). The link needs the admin host (`https://admin.<host>/{locale}/login`), which `Shared` does not currently carry.
- **CORS preflights die behind the setup gate.** The gate (`app.rs:86`) is outside the API router's `cors` layer (`app.rs:65`), so while the instance is unconfigured an `OPTIONS` preflight from an allowed origin gets the 503 envelope without any `Access-Control-*` header, and a frontend on another origin sees an opaque CORS error instead of `not_configured`. No privacy effect (the gate's answer is the same for everyone); a usability note for the orchestrator.
- **`init --env` keeps a world-readable mode.** `init.rs:116-124` copies the existing file's permissions onto the rewritten file, as SPEC §8 says ("keeping its permissions"). An `.env` that is 0644 (common for files fetched with `curl -o`) therefore ends up holding `SHH_SECRET_KEY` and `SHH_ADMIN_TOKEN` readable by every local user. Spec-conformant, operator credentials, so not a finding; a one-line warning on stdout when the mode allows group or other read would be cheap hardening.
- **Two instances on one S3 bucket delete each other's objects.** `collect_orphans` (storage.rs:137-156) deletes every `blobs/<22 chars>` object not referenced by *this* database. Not a privacy matter (it is data loss on a misconfiguration the docs do not forbid explicitly); for pass 2 or the deployment guide.
- **`sessionStorage` is persisted to disk by browsers.** `ui/claims.ts` keeps `shh-claim:<base64url SHA-256(lookup)>` → `{claimToken, expiresAt}` for the claim window, as SPEC §10 documents. Firefox and Chromium write `sessionStorage` to their session-restore files, so for up to the window (and until the page runs `prune()` again) the claim token and the lookup hash can sit in the recipient's browser profile on disk, alongside the share URL the browser keeps anyway. The recipient's own device is outside this pass's four threat actors; noted so the threat-model page can mention it if wanted. Nothing else about a secret is written to browser storage (`localStorage` holds only the theme, `ui/chrome.ts:46-58`).
